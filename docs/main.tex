    \renewcommand{\abstractname}{Resumen}
    \begin{abstract}
        Este Trabajo Fin de Grado presenta \emph{PoseCoach}, una aplicación web
        de fitness que integra un módulo de corrección postural ejecutado
        íntegramente en el navegador. El sistema combina un catálogo de
        ejercicios con vídeos demostrativos, valoraciones, comentarios y
        favoritos, con un módulo de análisis que evalúa la técnica de ejecución
        a partir de un vídeo aportado por el usuario. El análisis se apoya en la
        estimación de pose de MediaPipe para obtener los puntos clave del cuerpo,
        a partir de los cuales se calculan ángulos articulares y alineaciones que
        un motor de reglas traduce en una puntuación y en correcciones concretas.
        Todo el procesamiento se realiza en el cliente, sin que el vídeo llegue a
        salir del dispositivo. La aplicación se ha desarrollado con una
        arquitectura cliente-servidor, con frontend en Angular y una API REST en
        Spring Boot con persistencia en MySQL.
        \medskip

        \noindent\textbf{Palabras clave:} corrección postural, estimación de
        pose, MediaPipe, fitness, Angular, Spring Boot, aplicación web
    \end{abstract}

    \renewcommand{\abstractname}{Abstract}
    \begin{abstract}
        This Bachelor's Thesis presents \emph{PoseCoach}, a web-based fitness
        application featuring a posture-correction module that runs entirely in
        the browser. The system combines an exercise catalogue with
        demonstration videos, ratings, comments and favourites, together with an
        analysis module that evaluates exercise technique from a user-supplied
        video. The analysis relies on MediaPipe pose estimation to obtain body
        landmarks, from which joint angles and alignments are computed and turned
        into a score and specific corrections by a rule engine. All processing
        takes place on the client, so the video never leaves the device. The
        application follows a client-server architecture, with an Angular
        frontend and a Spring Boot REST API backed by a MySQL database.
        \medskip

        \noindent\textbf{Keywords:} posture correction, pose estimation,
        MediaPipe, fitness, Angular, Spring Boot, web application
    \end{abstract}

    \section{Contextualización y motivación}

    En la actualidad, el interés por la actividad física y el entrenamiento
    personal ha crecido notablemente, impulsado por la concienciación sobre
    la salud y el bienestar. Sin embargo, una gran parte de las personas que
    realizan ejercicio lo hacen sin supervisión directa de un profesional, lo
    que puede dar lugar a una ejecución incorrecta de los ejercicios,
    disminuyendo su efectividad y aumentando el riesgo de lesiones. Esta
    problemática se acentúa en los entrenamientos realizados en casa de forma
    autónoma, donde el usuario carece de mecanismos objetivos para evaluar su
    técnica.
    
    Paralelamente, el desarrollo de aplicaciones web y móviles en el ámbito
    del fitness ha facilitado el acceso a rutinas de entrenamiento, catálogos
    de ejercicios y herramientas de seguimiento. No obstante, muchas de estas
    soluciones se limitan a ofrecer contenido estático o guías visuales, sin
    proporcionar recursos que ayuden a corregir errores posturales de forma
    objetiva.
    
    En este contexto, las técnicas de visión por computador, y en particular
    la estimación de la postura corporal, ofrecen nuevas posibilidades para
    analizar el movimiento humano a partir de imágenes o vídeos. Estas
    técnicas permiten detectar puntos clave del cuerpo y calcular métricas
    como ángulos articulares y alineaciones, lo que abre la puerta a sistemas
    de apoyo capaces de evaluar la ejecución de determinados ejercicios sin
    necesidad de equipamiento especializado.
    
    Este Trabajo Fin de Grado propone el desarrollo de una aplicación web de
    fitness que combine funcionalidades tradicionales de seguimiento de
    entrenamiento con un sistema de corrección postural. A diferencia de otras
    soluciones existentes, centradas exclusivamente en el consumo de contenido
    o en el registro de entrenamiento, este proyecto integra el análisis
    postural como elemento clave del sistema, sin sustituir a un entrenador
    profesional, sino sirviendo como herramienta de apoyo para mejorar la
    calidad del entrenamiento autónomo.


    \section{Objetivos}
    
    \subsection{Objetivo general}
    
    El objetivo principal de este Trabajo Fin de Grado es desarrollar una
    aplicación web de fitness que permita a los usuarios consultar ejercicios
    guiados, realizar un seguimiento de su entrenamiento y recibir apoyo en la
    corrección de la postura durante la ejecución de determinados ejercicios
    mediante técnicas de estimación de pose, mejorando la calidad del
    entrenamiento autónomo sin sustituir la supervisión de un profesional.
    
    \subsection{Objetivos específicos}
    
    \begin{itemize}
        \item \textbf{Gestión de usuarios:} diseñar e implementar un sistema de
        registro, autenticación e inicio de sesión que permita gestionar el
        perfil personal de forma segura.
        \item \textbf{Catálogo de ejercicios:} desarrollar un catálogo con
        filtrado por criterios como grupo muscular o nivel de dificultad.
        \item \textbf{Visualización detallada de ejercicios:} proporcionar una
        vista de detalle con descripción, consejos de ejecución y vídeos de
        ejemplo embebidos desde plataformas externas como YouTube.
        \item \textbf{Valoraciones y comentarios:} implementar funcionalidades
        sociales que permitan puntuar ejercicios mediante estrellas y compartir
        comentarios, mostrando las valoraciones de forma agregada.
        \item \textbf{Ejercicios favoritos:} permitir marcar ejercicios como
        favoritos y acceder a una vista con la lista personalizada.
        \item \textbf{Corrección postural asistida:} integrar un sistema de
        análisis postural que evalúe la ejecución a partir de vídeos locales,
        procesados directamente en el navegador.
        \item \textbf{Cálculo de métricas de ejecución:} calcular métricas
        básicas, como ángulos articulares y alineaciones, adaptadas a cada
        ejercicio.
        \item \textbf{Generación de feedback:} mostrar la puntuación global
        junto con mensajes de corrección y recomendaciones claras.
        \item \textbf{Desarrollo full-stack:} diseñar e implementar una
        arquitectura cliente-servidor con frontend en Angular y backend con
        API REST, autenticación y persistencia de datos.
    \end{itemize}


    \section{Metodología y gestión del proyecto}
    \label{subsec:metodologia}
    \subsection{Metodología incremental iterativa (ágil)}

    El desarrollo de este proyecto sigue una metodología incremental iterativa,
    basada en los principios ágiles y adaptada a un entorno de trabajo
    individual. El trabajo se organiza en incrementos de corta duración, cada
    uno de los cuales da lugar a una versión funcional parcial de la
    aplicación, lo que permite evaluar el progreso de forma continua y validar
    las decisiones de diseño adoptadas. Se parte de un \textit{product backlog}
    inicial con las funcionalidades principales, descompuestas en tareas
    priorizadas según su relevancia; cada incremento comienza por los
    componentes básicos del sistema y evoluciona hacia funcionalidades más
    complejas, como el análisis postural, revisándose al finalizar para
    detectar errores de forma temprana.

    \subsection{Gestión con Jira: backlog, sprints y tableros}
    \label{subsec:jira}
    
    La gestión del proyecto se apoya en Jira como herramienta de planificación
    y seguimiento. El trabajo se estructura en \textit{épicas}, cada una
    correspondiente a un bloque funcional del sistema: arranque del entorno
    (E0), gestión de usuarios (E1), catálogo de ejercicios (E2),
    funcionalidades sociales (E3), corrección postural (E4) y pruebas y cierre
    (E5), además de una épica específica para la redacción de la memoria. Cada
    épica se descompone en \textit{historias} o tareas, que a su vez se
    detallan a nivel diario para mantener objetivos pequeños y alcanzables.
    
    La planificación temporal se organiza en \textit{sprints} de una semana de
    duración. Cada sprint agrupa las tareas de una épica que pueden completarse
    en ese periodo; las épicas más extensas, como la de corrección postural, se
    reparten en varios sprints consecutivos. El avance de cada tarea se controla
    mediante un tablero (\textit{board}) que refleja su estado, lo que
    proporciona una visión continua del progreso y permite mantener un ritmo de
    trabajo constante. La Figura~\ref{fig:jira-cronograma} muestra el cronograma
    del proyecto en Jira, con la distribución de las épicas a lo largo del tiempo.

\section{Aplicaciones de fitness actuales}

    El mercado de aplicaciones de fitness ha crecido de forma sostenida en los
    últimos años, ofreciendo rutinas de entrenamiento, catálogos de ejercicios y
    herramientas de seguimiento de la actividad. Atendiendo a su enfoque, pueden
    distinguirse varias categorías. Un primer grupo lo forman las aplicaciones de
    seguimiento y registro, como \textit{Strava}~\cite{strava} o \textit{MyFitnessPal}~\cite{myfitnesspal},
    centradas en cuantificar la actividad, distancias, calorías o
    repeticiones, pero sin evaluar cómo se ejecuta el movimiento. Un segundo
    grupo lo constituyen las aplicaciones de rutinas guiadas, como
    \textit{Nike Training Club}~\cite{niketraining} o \textit{Freeletics}~\cite{freeletics},
    que proponen ejercicios mediante vídeos e instrucciones, de modo que la
    corrección de la técnica queda a cargo del propio usuario, que carece de
    una referencia objetiva sobre su ejecución.

    Un tercer grupo, más reciente, incorpora el análisis del movimiento del
    usuario mediante la cámara del dispositivo. Es el caso de propuestas como
    \textit{Kaia Health}~\cite{kaia}, orientada a la fisioterapia, o de sistemas comerciales
    de \textit{fitness} con cámara que ofrecen retroalimentación en tiempo real.
    Estas soluciones se aproximan al objetivo de este trabajo, si bien suelen
    depender de procesamiento en servidor, de suscripciones de pago o de
    hardware específico, y rara vez explicitan cómo tratan la privacidad del
    vídeo capturado. La propuesta de este trabajo se sitúa en esta última
    categoría, con la particularidad de realizar todo el análisis en el propio
    navegador, sin que el vídeo abandone el dispositivo.

    \section{Estimación de pose y corrección postural}

    La corrección postural asistida se apoya en la \textit{estimación de pose}
    (\textit{pose estimation}), una técnica de visión por computador que localiza
    en una imagen o un vídeo los puntos clave del cuerpo humano, articulaciones
    y referencias anatómicas, y devuelve sus coordenadas. A partir de esos
    puntos pueden calcularse magnitudes geométricas como ángulos articulares y
    alineaciones, que constituyen la base para evaluar la ejecución de un
    ejercicio sin necesidad de sensores ni equipamiento especializado.

    Entre las soluciones de referencia destaca \textit{OpenPose}~\cite{openpose}, desarrollada
    por la Universidad Carnegie Mellon, uno de los primeros sistemas capaces de
    estimar la pose de múltiples personas en tiempo real, aunque con unos
    requisitos de cómputo, habitualmente una tarjeta gráfica dedicada, que
    dificultan su uso en el lado del cliente. Frente a este enfoque,
    \textit{MediaPipe}~\cite{mediapipe}, desarrollada por Google, ofrece modelos de estimación de
    pose optimizados para ejecutarse en dispositivos de recursos limitados,
    incluido el navegador, lo que la hace especialmente adecuada para una
    aplicación web. Su modelo de pose, basado en la arquitectura
    \textit{BlazePose}~\cite{blazepose}, detecta treinta y tres puntos del cuerpo y prioriza un
    equilibrio entre precisión y rendimiento que permite el análisis en tiempo
    real sobre hardware convencional.

    El uso de la estimación de pose para evaluar ejercicio físico cuenta ya con
    respaldo en la literatura. Trabajos como el de \textcite{myer2014} demuestran
    que la técnica de ejercicios como la sentadilla puede descomponerse en un
    conjunto de factores observables y evaluables, un enfoque que este proyecto
    adopta al traducir dichos factores en reglas aplicadas sobre los ángulos
    medidos. Conviene precisar, no obstante, que estas técnicas presentan
    limitaciones inherentes: la estimación bidimensional no capta la profundidad
    y su fiabilidad depende del ángulo de la cámara y de las condiciones de la
    grabación, aspectos que delimitan el alcance de cualquier herramienta basada
    en ellas y que se abordan explícitamente en el diseño del sistema.
    
    \section{Aportación diferencial del proyecto}
    
    A diferencia de las soluciones existentes, centradas en el consumo de
    contenido o en el registro del entrenamiento, este proyecto integra el
    análisis postural como un elemento central del sistema, manteniendo un
    alcance realista acorde a un Trabajo Fin de Grado. El objetivo no es
    sustituir a un entrenador profesional, sino ofrecer una herramienta de
    apoyo que ayude a reducir errores comunes en el entrenamiento autónomo.

    \section{Frontend: Angular y SCSS}

    La interfaz de usuario se desarrolla con Angular~\cite{angular}, un
    \textit{framework} de código abierto para la construcción de aplicaciones
    web de página única (\textit{SPA}) basado en TypeScript. Se emplea su modelo
    de componentes \textit{standalone} y su sistema de reactividad basado en
    \textit{signals}, valores que notifican automáticamente los cambios a quienes
    los consultan, lo que permite gestionar el estado de la interfaz sin recurrir
    a una biblioteca externa de gestión de estado. Para los estilos se utiliza
    SCSS~\cite{scss}, una extensión de CSS que aporta variables y anidamiento y
    facilita la definición de un sistema de diseño coherente.
    
    \section{Backend: Spring Boot, API REST y JWT}
    
    El servidor se implementa con Spring Boot~\cite{springboot}, un framework de Java que agiliza
    la creación de aplicaciones y servicios web. Expone una API REST que
    comunica el frontend con la lógica de negocio mediante peticiones HTTP en
    formato JSON. La seguridad se gestiona con Spring Security~\cite{springsecurity} y autenticación
    basada en JSON Web Tokens (JWT)~\cite{jwt}, que permiten un control de acceso sin
    estado en el servidor. La gestión de dependencias y la construcción del
    proyecto se realizan con Maven~\cite{maven}, y se emplea Lombok~\cite{lombok} para reducir código
    repetitivo en las clases del modelo. Para probar los endpoints de la API
    de forma aislada durante el desarrollo, sin depender del frontend,
    se ha utilizado Postman~\cite{postman}, una herramienta para construir y examinar peticiones HTTP.
    
    \section{Persistencia: MySQL y Docker}
    
    La información se almacena en MySQL~\cite{mysql}, un sistema gestor de bases de datos
    relacional. Para facilitar su despliegue y garantizar un entorno
    reproducible, la base de datos se ejecuta en un contenedor Docker~\cite{docker} con un
    volumen persistente, de modo que los datos se conservan entre reinicios sin
    necesidad de instalar MySQL directamente en el sistema anfitrión.
    
    \section{Visión por computador: MediaPipe Pose}

    El módulo de corrección postural se apoya en MediaPipe~\cite{mediapipe}, una biblioteca de
    Google para la aplicación de modelos de aprendizaje automático sobre
    imagen y vídeo. De su conjunto de soluciones se emplea la tarea
    \texttt{PoseLandmarker}, que detecta treinta y tres puntos clave del cuerpo
    humano (\textit{landmarks}) a partir de cada fotograma, cada uno con sus
    coordenadas y un valor de confianza. Se utiliza el paquete
    \texttt{@mediapipe/tasks-vision}, integrado en el proyecto de Angular como
    una dependencia más.

    El modelo admite tres variantes, \textit{lite}, \textit{full} y
    \textit{heavy}, que intercambian precisión por coste de cómputo. Se ha
    optado por la variante \textit{lite}, la más ligera, por resultar
    suficiente para el análisis de perfil que realiza la aplicación y permitir
    un procesamiento fluido en tiempo real sobre equipos de gama media, sin la
    penalización de las variantes de mayor tamaño.

    El procesamiento se ejecuta íntegramente en el navegador mediante
    WebAssembly (WASM), un formato binario que permite ejecutar código de alto
    rendimiento en el cliente a velocidad cercana a la nativa. Tanto los
    ficheros WASM del motor como el modelo de pose se sirven desde la propia
    aplicación, y no desde una red de distribución de contenido externa, lo que
    evita cualquier dependencia de red en tiempo de ejecución y resulta coherente
    con el despliegue reproducible mediante contenedores que exige el requisito
    RNF-05. Esta ejecución local es, además, la que hace posible cumplir el
    requisito RNF-02: el vídeo del usuario nunca abandona el dispositivo, ya que
    tanto la detección de pose como el cálculo de métricas se realizan en el
    navegador. A partir de los puntos detectados se calculan ángulos articulares
    y alineaciones, cuyo tratamiento se detalla en el
    Capítulo~\ref{cap:diseno}.

    relación adicionales. Lo mismo ocurre con los consejos de ejecución

    elementos, lo que da lugar a las tres tablas físicas recogidas en la

    dirección de reproducción embebida como la de la miniatura, sin necesidad

    ejercicio es la miniatura servida por la propia plataforma junto al enlace
    al vídeo original, lo que evita incorporar a la memoria y al repositorio
    ilustraciones anatómicas de terceros, algo especialmente pertinente dado

    Esta entidad almacena deliberadamente el mínimo de información ---la
    puntuación, el ejercicio y la fecha---, y nunca el vídeo ni las correcciones
    detalladas. No es una simplificación por conveniencia, sino una consecuencia
    del requisito RNF-02: las correcciones solo tienen sentido mientras el vídeo
    permanece cargado en el navegador y, como este nunca se transmite ni se
    almacena, conservarlas produciría una lista de avisos que apuntarían a
    instantes de un vídeo inexistente. El historial se concibe así como un resumen
    ---qué ejercicio se analizó, con qué puntuación y cuándo---, lo único cuya
    persistencia resulta coherente con el procesamiento local del vídeo.

    La decisión de diseño más relevante de este modelo es que los requisitos
    RF-05 y RF-06, que el enunciado presenta como funcionalidades separadas, se
    satisfacen con \textbf{una única entidad}. El motivo procede del diseño de
    la interfaz: la puntuación y el comentario se publican mediante un solo
    formulario y una sola acción, y cada comentario se muestra siempre
    acompañado de las estrellas de su autor. Modelarlos por separado habría
    obligado a reconstruir mediante una reunión de tablas algo que el usuario
    percibe como un único objeto, y habría permitido estados incoherentes, como
    un comentario sin puntuación asociada.

    De esa unificación se deriva que el atributo \texttt{content} admita valor
    nulo. Un usuario puede puntuar sin escribir nada, situación habitual y
    prevista por la interfaz, en cuyo caso la valoración computa en la media y
    en la distribución pero no aparece en el listado de comentarios. Esto
    explica que el número de valoraciones de un ejercicio sea siempre mayor o
    igual que el de comentarios, sin que ello suponga ninguna inconsistencia.

    Ambas entidades incorporan una restricción de unicidad sobre el par
    (usuario, ejercicio), que es el mecanismo que hace cumplir las reglas RN-01
    y RN-05, del mismo modo que ya ocurría con los campos \texttt{username} y
    \texttt{email} de \texttt{User}. El Capítulo~\ref{cap:implementacion} detalla
    por qué esta garantía se sitúa en la base de datos y no solo en la lógica de
    la aplicación.

    La entidad \texttt{Review} registra dos marcas temporales porque la
    valoración es modificable. Al sustituirse el contenido de la fila, la fecha
    de creación deja de describir el estado actual del dato, de modo que
    \texttt{updatedAt} recoge cuándo se fijó el valor vigente. La interfaz
    aprovecha ambas: ordena los comentarios por fecha de publicación, para que
    una corrección menor no altere su posición en la lista, y señala como
    editados aquellos en los que ambas fechas difieren.

    Merece justificación aparte que \texttt{Favorite} se haya modelado como una
    entidad y no como una relación de muchos a muchos entre \texttt{User} y
    \texttt{Exercise}, que es la construcción que JPA ofrece de forma directa
    para este caso. El motivo es que la relación posee un atributo propio: la
    fecha en que se marcó el favorito, que determina el orden del listado. Una
    relación de muchos a muchos genera una tabla intermedia capaz de albergar
    únicamente las dos claves ajenas, por lo que ese dato no tendría dónde
    almacenarse. En el momento en que una relación incorpora información
    propia, deja de ser una relación y pasa a ser una entidad.

    Por último, y conforme a la regla RN-06, la valoración media no figura como
    atributo de \texttt{Exercise}. Almacenarla habría permitido consultarla sin
    cálculo alguno, pero introduce un dato redundante que debe mantenerse
    sincronizado con cada alta, modificación y baja de valoración, y que queda
    incorrecto en cuanto una de esas actualizaciones falla. Se ha optado por
    calcularla en cada consulta; el Capítulo~\ref{cap:implementacion} detalla
    cómo se hace sin penalizar el rendimiento del listado.

    \section{Diseño de la API REST}

    que intercambia mensajes en formato JSON sobre HTTP. Cada operación se asocia
    a una ruta y a un verbo HTTP, y la respuesta se acompaña del código de estado
    HTTP correspondiente al resultado. El módulo de autenticación expone las
    rutas recogidas en la Tabla~\ref{tab:api-auth}, ambas públicas por no
    requerir un usuario autenticado previo.

    \begin{table}[htbp]
        \centering
        \begin{tabular}{lll}
            \toprule
            \textbf{Verbo} & \textbf{Ruta} & \textbf{Descripción} \\
            \midrule
            POST & /api/auth/register & Registro de un nuevo usuario \\
            POST & /api/auth/login    & Inicio de sesión y obtención del token \\
            \bottomrule
        \end{tabular}
        \caption{Rutas públicas del módulo de autenticación.}
        \label{tab:api-auth}

    En el registro, el cuerpo de la petición contiene el nombre de usuario, el
    correo y la contraseña. La respuesta emplea distintos códigos de estado según
    el resultado: \texttt{201 Created} si el usuario se crea correctamente,
    \texttt{400 Bad Request} si los datos no superan la validación (por ejemplo,
    un correo con formato incorrecto) y \texttt{409 Conflict} si el nombre de
    usuario o el correo ya están registrados.

    En el inicio de sesión, el cuerpo de la petición contiene el nombre de
    usuario y la contraseña. Si las credenciales son correctas, la respuesta es
    \texttt{200 OK} e incluye el token JWT que el cliente deberá presentar en
    las peticiones posteriores; si no lo son, la respuesta es
    \texttt{401 Unauthorized}. Por seguridad, el mensaje de error es idéntico
    tanto si el usuario no existe como si la contraseña es incorrecta, evitando
    así revelar qué nombres de usuario están registrados.

    Una vez autenticado, el usuario dispone además de las rutas recogidas en la
    Tabla~\ref{tab:api-users}, todas ellas privadas: exigen presentar un token
    JWT válido y operan siempre sobre el usuario identificado por dicho token,
    de modo que ningún usuario puede consultar ni modificar los datos de otro.

            \textbf{Verbo} & \textbf{Ruta} & \textbf{Descripción} \\
            \midrule

            \bottomrule

        \label{tab:api-users}
    \end{table}

    \subsection{Autenticación basada en tokens (JWT)}

    Para el control de acceso se ha optado por una autenticación basada en
    tokens JWT (\textit{JSON Web Token}) en lugar del modelo clásico de sesiones
    en el servidor. Un JWT es una credencial firmada digitalmente que el
    servidor entrega al usuario tras un inicio de sesión correcto y que este
    presenta en cada petición posterior. El token contiene la información
    necesaria para identificar al usuario (su nombre y su rol) y una fecha de
    caducidad, y va firmado con una clave secreta que solo conoce el servidor,
    lo que le permite verificar su autenticidad sin necesidad de almacenar
    ninguna sesión.

    La principal ventaja de este enfoque es que el servidor es \textit{sin
    estado} (\textit{stateless}): no necesita guardar información de sesión de
    cada usuario, lo que simplifica la arquitectura y facilita la escalabilidad.
    Este modelo encaja además de forma natural con una arquitectura desacoplada
    de frontend y backend que se comunican mediante una API REST, en la que el
    cliente conserva el token y lo adjunta en la cabecera \texttt{Authorization}
    de sus peticiones. Conviene precisar que el token va firmado, pero no
    cifrado, por lo que nunca se incluye en él información sensible como la
    contraseña.

    Conviene subrayar que la protección de rutas en el cliente (mediante un
    \textit{guard} de Angular) cumple únicamente una función de experiencia de
    usuario: evita mostrar vistas privadas cuando no hay sesión. La seguridad
    efectiva reside siempre en el servidor, que revalida el token en cada
    petición con independencia de lo que decida el cliente.

    se incluye en el resultado si trabaja \textit{alguno} de los grupos

    ejercicio implicase simultáneamente todos los grupos marcados, porque
    produciría listados casi vacíos ante cualquier combinación de dos o más
    grupos. El filtro por dificultad, en cambio, admite un único valor, dado
    que los tres niveles son mutuamente excluyentes.

    tamaño crezca sin cota al ampliarse el catálogo. Para ello se define un objeto
    de transferencia propio en lugar de serializar la estructura de paginación del
    marco de trabajo, que expone numerosos campos internos sin garantía de
    estabilidad entre versiones; el objeto propio publica solo lo que el cliente
    necesita, incluido el número total de resultados.

    vista necesita.

        \label{tab:api-social}
    \end{table}

    El diseño de estas rutas incorpora tres decisiones que conviene explicitar.

    La primera es que el recurso de la valoración se nombra \textbf{en
    singular} y se manipula con el verbo \texttt{PUT}. La ruta no designa «las
    valoraciones del ejercicio», sino «mi valoración de este ejercicio», que
    por definición es única, y \texttt{PUT} expresa en HTTP la intención de
    dejar un recurso en un estado determinado, frente a \texttt{POST}, que
    solicita añadir un elemento más a una colección. De este modo, la regla
    RN-01 no depende de una comprobación que pudiera olvidarse: sencillamente
    \textbf{no existe ninguna operación en la API capaz de crear una segunda
    valoración}. Como consecuencia, publicar por primera vez y editar una
    valoración existente son la misma operación.

    La segunda es que el identificador del usuario no aparece en ninguna ruta.
    La identidad se obtiene siempre del token presentado en la cabecera de la
    petición. Combinado con lo anterior, esto tiene un efecto directo sobre la
    regla RN-04: al no aceptar ninguna ruta el identificador de una valoración
    concreta, no es posible expresar la petición «elimina la valoración número
    57», y con ello se elimina por diseño la posibilidad de una referencia
    directa insegura a objetos, conocida como \textit{IDOR}
    (\textit{Insecure Direct Object Reference}), que constituye una de las
    vulnerabilidades más frecuentes en aplicaciones web.

    La tercera afecta al favorito. Aunque la interfaz lo presente como un
    control que alterna entre dos estados, se ha descartado exponer una única
    ruta de conmutación en favor de un \texttt{PUT} y un \texttt{DELETE}
    explícitos. Una operación de conmutación depende del estado previo del
    recurso, de modo que dos peticiones consecutivas emitidas con rapidez y
    procesadas en orden distinto al esperado dejarían el favorito en un estado
    impredecible. Con verbos explícitos cada petición declara el estado final
    deseado y resulta \textit{idempotente}: repetirla no produce ningún efecto
    adicional. Esta propiedad es además la que permite al cliente aplicar sus
    cambios de forma anticipada, como se detalla en el
    Capítulo~\ref{cap:implementacion}.

    La Tabla~\ref{tab:api-social-codigos} recoge los códigos de estado de estas
    operaciones.

    \subsection{Formato de las respuestas de error}

    Todas las respuestas de error de la API comparten una misma estructura, un
    objeto JSON con un único campo \texttt{message} que contiene un texto
    destinado a mostrarse al usuario. Se exceptúan los errores de validación de
    los datos de entrada, que devuelven un objeto con una entrada por cada
    campo rechazado, ya que en ese caso no existe un único error sino tantos
    como campos incorrectos, y la interfaz necesita asociar cada mensaje al
    campo que le corresponde. Unificar el resto de respuestas permite que el
    cliente disponga de un único punto de lectura del mensaje de error con
    independencia de la operación que haya fallado.

    \section{Diseño del módulo de corrección postural}
    El módulo de corrección postural constituye la aportación diferencial del
    sistema y concentra las decisiones de diseño más específicas de este
    trabajo. Su cometido es evaluar la técnica de ejecución de un ejercicio a
    partir de un vídeo aportado por el usuario y traducir esa evaluación en una
    puntuación y en un conjunto de correcciones comprensibles. Toda la cadena de
    procesamiento, desde la lectura del vídeo hasta el cálculo de la nota, se
    ejecuta en el navegador, conforme al requisito RNF-02.

    \subsection{Visión general del proceso}

    El análisis se organiza como una secuencia de etapas en la que cada una
    transforma la salida de la anterior, desde el vídeo en bruto hasta un
    resultado interpretable. La Figura~\ref{fig:pipeline-postural} representa
    esta secuencia.

    El vídeo, seleccionado del dispositivo del usuario, se reproduce en el
    cliente sin llegar a transmitirse a ningún servidor. Durante la
    reproducción, cada fotograma se entrega al modelo de estimación de pose, que
    devuelve la posición de los puntos clave del cuerpo. A partir de esos puntos
    se calculan las métricas geométricas relevantes, esencialmente ángulos
    articulares y alineaciones, que constituyen la señal sobre la que opera el
    resto del proceso. Esa señal se segmenta después según la naturaleza del
    ejercicio: en los ejercicios dinámicos se identifican las repeticiones
    individuales, mientras que en los estáticos se considera cada instante por
    separado. Sobre las muestras así obtenidas se evalúa un conjunto de reglas
    técnicas, cada una de las cuales penaliza una desviación concreta, y la suma
    de sus penalizaciones determina la puntuación final y las correcciones que se
    muestran al usuario.

    Esta organización por etapas cumple una función que va más allá de lo
    descriptivo: cada etapa tiene una responsabilidad única y una interfaz
    definida con las contiguas, lo que permite razonar sobre ellas de forma
    independiente y, como se verá, sustituir la lógica específica de un ejercicio
    sin alterar el resto de la cadena. Las secciones siguientes detallan las
    etapas que concentran las decisiones de diseño: el cálculo de métricas, la
    extracción de muestras y el modelo de puntuación.

    \subsection{Cálculo de métricas geométricas}

    El modelo de estimación de pose devuelve, para cada fotograma, treinta y
    tres puntos clave del cuerpo, cada uno con sus coordenadas en el plano de la
    imagen y un valor de confianza que indica la fiabilidad de la detección. Las
    coordenadas están normalizadas al intervalo $[0,1]$: la horizontal respecto
    a la anchura de la imagen y la vertical respecto a su altura. El análisis se
    limita a la vista de perfil, decisión cuyo alcance se justifica más adelante,
    por lo que de cada articulación se emplean los puntos de un único costado.

    La métrica fundamental del sistema es el ángulo que forman tres puntos del
    cuerpo en el vértice central: el de la rodilla (cadera--rodilla--tobillo)
    para la sentadilla, o el de la cadera (hombro--cadera--tobillo) para la
    plancha, entre otros. Dados tres puntos $A$, $B$ y $C$, el ángulo en el
    vértice $B$ se obtiene a partir de los vectores $\vec{BA}$ y $\vec{BC}$
    mediante la definición del producto escalar:

    \begin{equation}
        \theta = \arccos\!\left(
            \frac{\vec{BA} \cdot \vec{BC}}
                 {\lVert \vec{BA} \rVert \, \lVert \vec{BC} \rVert}
        \right)
        \label{eq:angulo}
    \end{equation}

    El resultado es un ángulo en el intervalo $[0^\circ, 180^\circ]$. Su cálculo
    se ha aislado en una función pura, sin dependencia del resto del sistema, lo
    que la convierte en la primera pieza del proyecto verificada mediante pruebas
    unitarias automatizadas, según se detalla en el
    Capítulo~\ref{cap:pruebas}.

    Dos aspectos de este cálculo requieren precisión, ya que condicionan la
    corrección del resultado.

    El primero es la \textbf{corrección de la relación de aspecto}. Dado que las
    coordenadas horizontal y vertical se normalizan por magnitudes distintas, la
    anchura y la altura de la imagen, una misma distancia real se representa
    con valores normalizados diferentes según su orientación cuando el vídeo no
    es cuadrado, que es el caso habitual. Emplear las coordenadas normalizadas
    directamente distorsionaría los ángulos. Antes de aplicar la
    Ecuación~\ref{eq:angulo} se restituye por tanto la proporción original,
    multiplicando la coordenada horizontal por la relación de aspecto del vídeo,
    de modo que ambas queden expresadas en una unidad común.

    El segundo es el \textbf{convenio angular}. El ángulo calculado mediante la
    Ecuación~\ref{eq:angulo} es el \textit{ángulo interior} del vértice: con la
    pierna completamente extendida, la rodilla mide aproximadamente $180^\circ$,
    y en una flexión profunda, en torno a $60^\circ$. La literatura biomecánica,
    en cambio, suele expresar la postura mediante el \textit{ángulo de flexión},
    que es el complementario del anterior:

    \begin{equation}
        \theta_{\text{interior}} = 180^\circ - \theta_{\text{flexión}}
        \label{eq:convenio}
    \end{equation}

    Ambos convenios coinciden en $90^\circ$, valor de referencia habitual, lo que
    facilita que la diferencia pase inadvertida; sin embargo, difieren en
    cualquier otro punto. Todos los umbrales que se definen en este trabajo se
    expresan en ángulo interior, el que produce directamente la
    Ecuación~\ref{eq:angulo}, y los valores tomados de la literatura se convierten
    a ese convenio antes de emplearse. Explicitar esta correspondencia evita una
    fuente de error entre la fuente consultada y el valor implementado.

    Por último, no todos los fotogramas contribuyen al análisis. Los puntos
    clave de la pierna o el tronco pueden detectarse con baja confianza cuando
    quedan parcialmente ocultos o la iluminación es deficiente, en cuyo caso el
    fotograma se descarta antes de incorporarse a la señal, para no introducir
    ruido en las métricas. El criterio con el que se elige el costado visible y
    se filtran los fotogramas poco fiables se apoya en el valor de confianza que
    acompaña a cada punto, y se detalla en el Capítulo~\ref{cap:implementacion}.

    \subsection{Abstracción de analizadores}

    Los ejercicios que el sistema evalúa no comparten la misma naturaleza. La
    sentadilla es un ejercicio \textbf{dinámico}: consiste en una serie de
    repeticiones, y su técnica se juzga en instantes concretos de cada una, la
    profundidad, en el punto más bajo; la extensión, al final del ascenso. La
    plancha, en cambio, es un ejercicio \textbf{estático}: no hay repeticiones,
    sino una postura que debe sostenerse en el tiempo, de modo que su técnica se
    evalúa de forma continua a lo largo de toda la ejecución.

    Esta diferencia podría sugerir la necesidad de dos módulos de análisis
    independientes. Sin embargo, un examen más detenido revela que ambos
    ejercicios comparten la mayor parte del proceso: los dos calculan ángulos a
    partir de los mismos landmarks, los dos evalúan un conjunto de reglas
    técnicas y los dos derivan de ellas una puntuación con el mismo criterio. La
    única etapa que difiere entre ellos es la \textbf{extracción de muestras}: la
    forma en que la señal continua de métricas se convierte en el conjunto de
    observaciones concretas sobre las que se aplican las reglas.

    El diseño se articula en torno a esa observación. Se define un
    \textbf{motor de puntuación común}, independiente del ejercicio, que recibe
    un conjunto de muestras y un conjunto de reglas y produce la puntuación y las
    correcciones. Cada ejercicio se modela como un \textbf{analizador} cuya única
    responsabilidad propia es extraer las muestras de la señal, y que delega en
    el motor común todo lo demás. En términos de la señal del ángulo:

    \begin{itemize}
        \item El analizador de la \textbf{sentadilla} identifica las
        repeticiones y produce \textit{una muestra por repetición}, tomada en el
        instante relevante de cada una.
        \item El analizador de la \textbf{plancha} produce \textit{una muestra
        por fotograma}, ya que en un ejercicio sostenido cada instante es una
        observación válida de la postura.
    \end{itemize}

    La consecuencia de este diseño es que las reglas de cada ejercicio no son
    código, sino \textbf{datos}: una tabla de condiciones que el motor común
    interpreta. Esta propiedad se validó de forma tangible al ampliar el sistema
    de dos a cuatro ejercicios: partiendo de la sentadilla y la plancha, la
    incorporación de la \textbf{flexión} y la \textbf{zancada} no requirió
    modificar el motor de puntuación ni la detección de repeticiones, sino
    únicamente definir la tabla de reglas de cada una y elegir qué ángulo medir.
    La flexión reutiliza la extracción de muestras por repetición de la
    sentadilla, midiendo el ángulo del codo en lugar del de la rodilla, y
    combina, además, una regla de alineación del cuerpo análoga a la de la
    plancha; la zancada es dinámica como la sentadilla y comparte con ella la
    lógica de detección, con umbrales propios. La abstracción queda así
    justificada no por una generalización anticipada, sino por cuatro casos
    reales: dos patrones cualitativamente distintos, dinámico y estático, y
    la extensión efectiva del sistema sin tocar su núcleo.

    Por su dificultad, la extracción de muestras del caso dinámico merece
    detallarse. Contar las repeticiones de una sentadilla equivale a localizar
    los mínimos de la señal del ángulo de rodilla: cada repetición es un descenso
    seguido de un ascenso. El problema es que esa señal no es limpia, sino que
    presenta pequeñas oscilaciones, procedentes tanto del movimiento real como
    de la imprecisión de la estimación de pose, de modo que una detección
    ingenua de mínimos contaría repeticiones inexistentes ante cualquier temblor.
    La solución adoptada combina dos mecanismos: un suavizado previo de la señal
    mediante una media móvil, que atenúa el ruido de alta frecuencia, y una
    \textbf{banda de histéresis} en la detección, que exige que el ángulo cruce
    dos umbrales distintos, uno para dar comienzo a la repetición y otro,
    más alto, para darla por concluida, en lugar de uno solo. La franja
    comprendida entre ambos actúa como zona muerta que impide que una oscilación
    en torno a un único valor se contabilice como varias repeticiones. Los
    umbrales que gobiernan esta detección son independientes de los que evalúan
    la corrección técnica: los primeros determinan qué constituye una
    repetición, y los segundos, si esa repetición es correcta.

    \subsection{Modelo de puntuación}

    La evaluación de la técnica se apoya en un modelo de reglas y penalizaciones
    común a todos los ejercicios. Cada ejercicio define un conjunto de reglas, y
    cada regla comprueba un aspecto técnico concreto, la profundidad de una
    sentadilla, la alineación de una plancha, sobre cada una de las muestras
    extraídas. A cada regla se le asigna una \textbf{penalización máxima}, y el
    diseño impone que la suma de las penalizaciones máximas de un ejercicio sea
    exactamente $100$. Esta condición garantiza que una ejecución perfecta, en la
    que ninguna regla se incumple, obtenga la puntuación máxima, y que el peor
    caso posible corresponda a una puntuación nula, sin necesidad de recortar
    artificialmente el resultado.

    La penalización de cada regla no es de todo o nada, sino \textbf{proporcional
    a la fracción de muestras que la incumplen}. Si $p_i$ es la penalización
    máxima de la regla $i$ y $f_i$ la fracción de muestras que la incumplen, la
    puntuación final se obtiene como:

    \begin{equation}
        \text{nota} = 100 - \sum_{i} p_i \, f_i
        \label{eq:puntuacion}
    \end{equation}

    Este carácter proporcional es lo que distingue una ejecución con un fallo
    puntual de otra sistemáticamente incorrecta: fallar la profundidad en dos de
    ocho repeticiones penaliza la cuarta parte que fallarla en todas. Además, la
    fracción incumplida determina también la gravedad con que se presenta cada
    corrección al usuario, leve o grave, de modo que el color y el mensaje
    de la interfaz se derivan del propio dato y no de una decisión arbitraria.

    A partir de la puntuación se establece una valoración cualitativa mediante
    tres umbrales: se considera correcta una ejecución de $80$ puntos o más,
    mejorable entre $50$ y $79$, y necesitada de revisión por debajo de $50$.
    Estos cortes constituyen un criterio orientativo propio, an\'alogo al de una
    calificación, y no una escala clínica. Conviene subrayar, en este sentido,
    que la finalidad del sistema es servir de apoyo al entrenamiento autónomo y
    no sustituir la valoración de un profesional.

    \subsection{Reglas de la sentadilla}

    Las reglas de la sentadilla se apoyan en la literatura biomecánica del
    ejercicio. El marco de referencia lo proporciona el trabajo de
    \textcite{myer2014}, que descompone la técnica de la sentadilla en un
    conjunto de factores evaluables, enfoque que este sistema adopta al traducir
    cada factor observable en una regla. El umbral de profundidad se apoya en la
    revisión biomecánica de \textcite{escamilla2001}, que caracteriza la
    sentadilla paralela, aquella en que el muslo alcanza la horizontal y la
    recomienda frente a la sentadilla profunda para articulaciones sanas. El
    sistema toma como objetivo esa profundidad paralela, empleando el ángulo de
    rodilla como aproximación operativa del criterio, y la evidencia de
    \textcite{han2017} sobre la activación muscular en función del ángulo de
    flexión respalda la relevancia de ese rango. La Tabla~\ref{tab:reglas-sentadilla}

    \subsection{Reglas de la plancha}

    La literatura de acondicionamiento físico describe la técnica correcta de la
    plancha de forma cualitativa, como el mantenimiento de una alineación
    corporal recta desde los hombros hasta los tobillos, sin que la cadera se
    hunda ni se eleve. Este principio se sostiene sobre el concepto de
    \textbf{neutralidad de la columna} bajo carga que desarrolla
    \textcite{mcgill2015}, para quien el fallo técnico en los ejercicios de
    estabilización del tronco se manifiesta precisamente como una desviación de
    esa posición neutra. Dado que dicha literatura no fija umbrales cinemáticos
    exactos, se ha llevado a cabo una \textbf{operativización propia} del
    criterio cualitativo: la alineación se mide como el ángulo
    hombro--cadera--tobillo, y se considera correcta dentro de una franja de
    $160^\circ$ a $180^\circ$, cuyo margen de tolerancia se ha ajustado

    \subsection{Alcance del análisis}

    El diseño descrito asume dos restricciones que conviene explicitar. La
    primera es que el análisis se realiza \textbf{únicamente sobre la vista de
    perfil}. La profundidad de una sentadilla o la alineación de una plancha se
    miden sobre el plano sagital del cuerpo, que es el que la cámara capta de
    lado; una grabación en diagonal proyecta ese plano de forma escorzada y
    degrada la fiabilidad de las métricas. Dar soporte a la vista frontal
    requeriría un conjunto de reglas distinto, la frontal permite detectar
    errores como el valgo de rodilla, invisibles de perfil, pero impide medir la
    profundidad, y queda planteado como línea de trabajo futuro.

    La segunda restricción deriva del propio modelo de estimación de pose, que es
    bidimensional y carece de puntos intermedios de la columna. Ello implica que
    ciertos errores no son observables: la curvatura de la espalda, que ocurre en
    un tramo que el modelo no representa, o cualquier desviación que requiera
    información de profundidad. El sistema mide, en consecuencia, la inclinación
    del tronco pero no su redondeo, y expone estas limitaciones de forma
    deliberada, ya que delimitan el alcance de una herramienta orientativa y no
    clínica.

    A estas dos restricciones se añade una condición sobre las propias
    condiciones de grabación: dado que el modelo procesa cada fotograma de forma
    independiente, una iluminación deficiente, en particular las sombras
    marcadas sobre el cuerpo, introduce bordes espurios que desestabilizan la
    detección de los puntos clave. El filtrado por confianza atenúa su efecto,
    pero no puede recuperar una grabación cuya iluminación es inadecuada de
    principio a fin, por lo que se recomienda al usuario grabar con buena luz,
    del mismo modo que se le indica hacerlo de perfil.

    El sistema implementa cuatro analizadores, sentadilla, plancha, flexión y
    zancada, que cubren los dos patrones de ejercicio contemplados, dinámico y
    estático. Otros ejercicios podrían incorporarse siguiendo el mismo esquema,
    definiendo su tabla de reglas sobre la infraestructura ya existente.

    El primer incremento no produjo funcionalidad visible, sino la

    \subsection{Modelo de dominio y persistencia}

    La entidad \texttt{User}, cuyos atributos se recogieron en la
    Tabla~\ref{tab:entidad-user}, se ha implementado como una entidad JPA
    (\textit{Java Persistence API}) anotada con \texttt{@Entity} y mapeada a la
    tabla \texttt{users}. Se ha optado por el nombre en plural porque
    \texttt{user} es una palabra reservada en MySQL, lo que evita conflictos en
    las consultas SQL generadas.

    El atributo \texttt{role} se persiste como cadena de texto mediante la
    anotación \texttt{@Enumerated(EnumType.STRING)}, de modo que en la base de
    datos se almacenan los valores \texttt{USER} y \texttt{ADMIN} de forma
    legible en lugar de un índice numérico. Los campos \texttt{username} y
    \texttt{email} se declaran con la restricción \texttt{unique}, garantizando
    su unicidad a nivel de base de datos. La fecha de alta (\texttt{createdAt})
    se asigna automáticamente antes de la primera inserción mediante un método
    anotado con \texttt{@PrePersist}. Para reducir el código repetitivo
    (\textit{getters}, \textit{setters} y constructores) se emplea la
    biblioteca Lombok.

    \subsection{Registro de usuarios y cifrado de contraseñas}

    El registro se implementa siguiendo una separación en capas. El controlador
    \texttt{AuthController} expone el endpoint \texttt{POST /api/auth/register} y
    recibe los datos en un objeto de transferencia (\textit{DTO})
    \texttt{RegisterRequest}, en lugar de la entidad \texttt{User} directamente.
    Así, el cliente solo puede enviar el nombre de usuario, el correo y la
    contraseña, y nunca campos sensibles como el identificador o el rol. Los
    datos se validan de forma declarativa mediante anotaciones de Jakarta Bean Validation (\texttt{@NotBlank}, \texttt{@Email},
    \texttt{@Size} y \texttt{@Pattern}), de modo que un correo con formato
    incorrecto, una contraseña demasiado corta o una contraseña que no cumple
    la política de complejidad se rechazan antes de procesar la petición. Dicha
    política exige un mínimo de ocho caracteres e incluir al menos una letra
    minúscula, una mayúscula y un dígito, y se aplica por igual en el registro
    y en el cambio de contraseña, de forma que ambas operaciones garantizan el
    mismo nivel mínimo de seguridad.
    
    La lógica de negocio reside en el servicio \texttt{AuthService}, que
    comprueba mediante el repositorio si el nombre de usuario o el correo ya
    existen y, en caso afirmativo, interrumpe el registro. Si los datos son
    válidos y únicos, cifra la contraseña y persiste el nuevo usuario con el rol
    \texttt{USER} por defecto.

    El cifrado de la contraseña es un aspecto central de la seguridad del
    sistema. Almacenarla en texto plano supondría un riesgo grave: si la base de
    datos se viera comprometida, todas las credenciales quedarían expuestas. Por
    ello se emplea BCrypt, una función de \textit{hash} diseñada específicamente
    para contraseñas. BCrypt es unidireccional, esto quiere decir que no permite recuperar la
    contraseña original a partir del \textit{hash}, incorpora una \textit{sal}
    (\textit{salt}) aleatoria que evita que dos contraseñas iguales produzcan el
    mismo resultado, y su coste de cálculo es ajustable, lo que la hace
    resistente a ataques de fuerza bruta. En la aplicación, el cifrado se realiza
    mediante un \texttt{BCryptPasswordEncoder} declarado como \textit{bean} de
    Spring. La Figura~\ref{fig:bcrypt-hash} muestra el resultado en la base de
    datos: la contraseña se almacena como un \textit{hash} con el prefijo
    \texttt{\$2a\$}, característico de BCrypt, y no en texto legible.

    \begin{figure}[htbp]
        \centering
        \includegraphics[width=0.95\textwidth]{img/bcrypt-hash.png}
        \caption{Contraseña almacenada cifrada con BCrypt en la tabla
        \texttt{users}, verificada mediante una consulta \texttt{SELECT}.}
        \label{fig:bcrypt-hash}
    \end{figure}

    Por último, las respuestas del endpoint se normalizan mediante un manejador
    global de excepciones (\texttt{@RestControllerAdvice}), que traduce los
    errores de validación a \texttt{400 Bad Request} y los conflictos de
    duplicado a \texttt{409 Conflict}, devolviendo en ambos casos un mensaje
    descriptivo en formato JSON.

    \subsection{Configuración de Spring Security}

    Al incorporar Spring Security, el marco protege por defecto todos los
    endpoints, lo que en un primer momento impedía el acceso al registro. Fue
    necesario definir una configuración explícita (\texttt{SecurityConfig}) que
    declara públicas las rutas bajo \texttt{/api/auth/**} y mantiene protegidas
    el resto. Además, al tratarse de una API REST sin estado, se deshabilitó la
    protección CSRF, cuyo propósito es evitar peticiones fraudulentas en
    formularios con sesión, no aplica en este modelo y, de mantenerse activa,
    bloquea las peticiones POST. La ausencia inicial de esta configuración se
    manifestó como respuestas \texttt{403 Forbidden}, lo que permitió identificar
    y corregir el problema durante la puesta en marcha.

    \subsection{Inicio de sesión y control de acceso}

    El inicio de sesión (\texttt{POST /api/auth/login}) localiza al usuario por su
    nombre y contrasta la contraseña recibida con el \textit{hash} almacenado
    mediante el método \texttt{matches} de BCrypt, que vuelve a cifrar la entrada y
    compara los resultados sin descifrar la original. Si las credenciales son
    válidas se emite un token JWT firmado con el nombre de usuario y el rol; en
    caso contrario se responde \texttt{401 Unauthorized}.

    El control de acceso a las rutas protegidas recae en un filtro
    (\texttt{JwtAuthenticationFilter}) que se ejecuta en cada petición: extrae el
    token de la cabecera \texttt{Authorization}, verifica su firma y su vigencia y,
    si es válido, establece la identidad del usuario en el contexto de seguridad de
    Spring. La configuración es \textit{stateless} y deja públicas únicamente las
    rutas de autenticación. Se comprobó accediendo a una ruta protegida
    (\texttt{GET /api/users/me}) sin token, que el servidor rechaza
    (Figura~\ref{fig:ruta-sin-token}), y con el token del inicio de sesión, que el
    servidor autoriza devolviendo los datos del usuario
    (Figura~\ref{fig:ruta-con-token}).

    \begin{figure}[htbp]
        \centering
        \includegraphics[width=0.9\textwidth]{img/ruta-sin-token.png}
        \caption{Acceso a una ruta protegida sin token: el servidor deniega la
        petición.}
        \label{fig:ruta-sin-token}
    \end{figure}

    \begin{figure}[htbp]
        \centering
        \includegraphics[width=0.9\textwidth]{img/ruta-con-token.png}
        \caption{Acceso a la misma ruta presentando un token JWT válido: el
        servidor autoriza y devuelve los datos del usuario.}
        \label{fig:ruta-con-token}

    La integración con el cliente web exigió dos ajustes adicionales en la
    configuración de seguridad. El primero es CORS (\textit{Cross-Origin Resource
    Sharing}): en desarrollo el frontend se sirve en el puerto 4200 y el backend en
    el 8080 y, al ser orígenes distintos, el navegador bloquea por seguridad las
    peticiones entre ambos salvo que el servidor las autorice; se declaró por ello
    el origen del cliente como permitido, habilitando también el método
    \texttt{OPTIONS} de la comprobación previa (\textit{preflight}) que el navegador
    envía antes de ciertas peticiones. Este ajuste es propio del entorno de
    desarrollo: en el despliegue con contenedores, donde cliente y servidor
    comparten un mismo origen tras el proxy inverso, la comprobación de origen deja
    de intervenir. El segundo ajuste corrige el código de estado ante un token
    inválido o caducado: Spring Security respondía por omisión \texttt{403
    Forbidden} ---que indica falta de permisos--- cuando el problema real es que el
    usuario no ha podido identificarse; se implementó un punto de entrada de
    autenticación que responde \texttt{401 Unauthorized} con un mensaje coherente
    con el resto de la API, de modo que el cliente distingue una sesión expirada de
    una falta de permisos.

    \subsection{Consulta y edición del perfil}

    Una vez autenticado, el usuario puede consultar y modificar su propio
    perfil a través de las rutas \texttt{GET /api/users/me} y
    \texttt{PUT /api/users/me}. En ambos casos el usuario se identifica a partir
    del token presentado en la petición, de modo que cada usuario solo puede
    acceder a sus propios datos y modificarlos, nunca los de otro. Por ello estas
    rutas son privadas y requieren un token válido; una petición sin token es
    rechazada por el servidor.

    La edición se limita al correo electrónico y a la contraseña; el nombre de
    usuario se mantiene fijo, ya que actúa como identificador dentro del token y
    modificarlo obligaría a renovar la sesión. Al actualizar el correo se
    comprueba que no esté ya en uso por otro usuario. El cambio de contraseña se
    realiza mediante una ruta específica (\texttt{PUT /api/users/me/password})
    que exige la contraseña actual antes de establecer la nueva, evitando así que
    una sesión abierta pueda usarse para cambiarla sin conocer la anterior.

        \section{Implementación de la interfaz web}

    Con el módulo de usuarios operativo en el servidor, se abordó la
    construcción de la interfaz web en Angular. Además de las pantallas propias
    del módulo de autenticación, en esta fase se establecieron las bases
    estructurales sobre las que se apoyaron los módulos siguientes: la
    organización del proyecto, el sistema de navegación, la comunicación con la
    API y la gestión de la sesión del usuario.

    \subsection{Estructura del proyecto y navegación}

    El código fuente se organiza en cuatro directorios que separan las
    responsabilidades: \texttt{core}, con los servicios y mecanismos
    transversales de la aplicación; \texttt{layouts}, con las plantillas de
    página; \texttt{pages}, con las vistas asociadas a cada ruta; y
    \texttt{shared}, con los componentes reutilizables.

    La aplicación se ha desarrollado con componentes \textit{standalone}, el
    modelo actual de Angular, en el que cada componente declara directamente sus
    propias dependencias en lugar de agruparse en módulos. Las rutas se definen
    de forma anidada: cada plantilla de página actúa como ruta padre y las
    vistas que comparten esa cabecera se declaran como rutas hijas, de modo que
    la estructura común se define una sola vez.

    Todas las vistas se cargan mediante carga diferida (\textit{lazy loading}):
    el código de cada pantalla se descarga únicamente cuando el usuario navega
    hasta ella, en lugar de incluirse en el paquete inicial. Esto reduce el
    tiempo de carga de la aplicación, una consideración especialmente relevante
    en un proyecto que incorporará el modelo de estimación de pose de MediaPipe.

    El acceso a las vistas privadas se controla mediante un \textit{guard} de
    ruta, una función que Angular ejecuta antes de activar una ruta y que
    decide si permite el acceso. El \textit{guard} implementado comprueba la
    existencia de una sesión activa y, en caso contrario, redirige al inicio de
    sesión. Como ya se ha señalado, esta comprobación cumple una función
    exclusivamente de experiencia de usuario: la seguridad efectiva reside en el
    servidor, que revalida el token en cada petición.

    En esta fase, la vista de inicio con sesión se implementó únicamente como
    marcador de posición, ya que su contenido dependía de funcionalidades
    abordadas más adelante: recibió parte de sus datos con el módulo de
    valoraciones y favoritos, y su composición definitiva se completó con el de
    corrección postural, del que procede el resumen de análisis recientes.

        \centering
        \includegraphics[width=\textwidth]{img/mockup-dashboard.png}
        \caption{Maqueta de la página de inicio con sesión iniciada.}

    \end{figure}

    \subsection{Formularios y validación en el cliente}

    Los formularios de la aplicación se han implementado con el enfoque de
    formularios reactivos de Angular, en el que la estructura y las reglas de
    validación se declaran en la clase del componente y no en la plantilla.
    Este enfoque mantiene la lógica de validación en el código, facilita su
    comprobación y permite reaccionar a los cambios de cada campo.

    Las reglas aplicadas replican exactamente las del servidor: campos
    obligatorios, formato de correo válido y la política de contraseña descrita
    anteriormente. Esta duplicidad es intencionada y responde a una separación
    de propósitos: la validación en el cliente proporciona respuesta inmediata y
    evita peticiones innecesarias, mientras que la del servidor constituye la
    garantía real, puesto que un cliente puede ser manipulado. Mantener ambas
    alineadas evita la situación indeseable de que el formulario acepte datos
    que el servidor terminará rechazando.

    En el formulario de registro, el cumplimiento de la política de contraseña
    se muestra en tiempo real mediante cuatro indicadores que se marcan a medida
    que la contraseña satisface cada requisito, y el botón de envío permanece
    deshabilitado mientras el formulario no sea válido. Se ha incorporado
    además un validador a nivel de grupo, necesario porque la coincidencia entre
    la contraseña y su repetición no puede evaluarse examinando un único campo
    de forma aislada.

    \subsection{Comunicación con la API}

    La comunicación con el servidor no se realiza desde los componentes, sino
    desde servicios especializados: \texttt{AuthService}, responsable del
    registro, el inicio de sesión y la sesión del usuario, y
    \texttt{UserService}, responsable de las operaciones sobre el perfil. Esta
    separación evita duplicar la lógica de acceso a la API en cada vista y
    mantiene los componentes centrados en la presentación.

    La dirección base de la API no se repite en cada servicio, sino que se
    declara en un único punto de configuración del cliente. Este valor cambia
    según el entorno: durante el desarrollo apunta al servidor local
    (\texttt{http://localhost:8080/api}), mientras que en la compilación de
    producción se sustituye por una ruta relativa (\texttt{/api}), de modo que
    las peticiones se dirijan al mismo origen desde el que se sirve la
    aplicación y sea el proxy inverso quien las encamine hacia el servidor. La
    sustitución la realiza el propio mecanismo de compilación de Angular, que
    reemplaza el fichero de configuración de desarrollo por el de producción.

    Esta centralización tuvo, no obstante, una excepción que pasó inadvertida
    hasta las pruebas del sistema ya contenerizado: uno de los servicios
    (\texttt{UserService}) conservaba la dirección del servidor escrita
    directamente en el código en lugar de tomarla del punto de configuración
    común. Mientras cliente y servidor se ejecutaron en la misma máquina durante
    el desarrollo, el fallo no se manifestó; al desplegar el sistema en
    contenedores, en cambio, esa dirección fija dejó de ser válida y la carga del
    perfil de usuario comenzó a fallar. La corrección consistió en hacer que
    dicho servicio tomara también la dirección del punto de configuración común,
    unificando su comportamiento con el del resto. La incidencia ilustra el valor
    de no duplicar un mismo dato de configuración: una única copia divergente
    basta para introducir un fallo que solo aparece al cambiar de entorno.

    La estructura de los mensajes intercambiados se declara mediante interfaces
    de TypeScript que reproducen los objetos de transferencia de datos del
    servidor. De este modo, cualquier discrepancia entre lo que el cliente envía
    y lo que el servidor espera se detecta en tiempo de compilación.

    Para adjuntar el token a las peticiones se emplea un \textit{interceptor},
    un mecanismo por el que pasan todas las peticiones HTTP antes de enviarse.
    El interceptor implementado añade la cabecera \texttt{Authorization} con el
    token cuando existe una sesión activa, lo que evita tener que incluirla
    manualmente en cada llamada y elimina el riesgo de omitirla por descuido.

    Un segundo interceptor supervisa las respuestas de error. Cuando el servidor
    responde con \texttt{401 Unauthorized} a una ruta protegida, interpreta que
    la sesión ha caducado, la cierra y redirige al inicio de sesión. Este
    mecanismo requirió una precisión importante: el mismo código de estado se
    emplea también para señalar credenciales incorrectas en el inicio de sesión
    y una contraseña actual errónea en el cambio de contraseña, situaciones en
    las que el usuario debe permanecer en el formulario viendo el mensaje de
    error. El interceptor excluye por tanto esas rutas, actuando únicamente
    cuando el \texttt{401} indica realmente una sesión inválida.

    \subsection{Gestión de la sesión}

    Tras un inicio de sesión correcto, el token JWT y los datos básicos del
    usuario se almacenan en el \texttt{localStorage} del navegador. Esta
    decisión permite que la sesión sobreviva a la recarga de la página y al
    cierre del navegador, evitando que el usuario deba volver a identificarse
    continuamente. Como contrapartida, el \texttt{localStorage} es accesible
    desde JavaScript, por lo que resulta sensible a ataques de tipo XSS; el
    riesgo se mitiga mediante la caducidad del token, que limita la ventana de
    uso de una credencial comprometida.

    El estado de la sesión se mantiene además en memoria mediante un
    \textit{signal}, el mecanismo de reactividad de Angular: se trata de un
    valor que notifica automáticamente a quienes lo consultan cuando cambia.
    Gracias a ello, la barra de navegación muestra las iniciales del usuario
    conectado y reacciona de forma inmediata al inicio y al cierre de sesión sin
    necesidad de gestionar manualmente ninguna actualización. Al arrancar la
    aplicación, este estado se reconstruye a partir de los datos almacenados en
    el navegador.

    En el cambio de contraseña se ha optado por cerrar la sesión y solicitar un
    nuevo inicio de sesión. Conviene precisar que el token emitido no depende de
    la contraseña, por lo que técnicamente seguiría siendo válido; forzar una
    nueva identificación constituye, sin embargo, una práctica recomendable, ya
    que confirma que el usuario conoce la credencial recién establecida.

    \subsection{Componentes reutilizables}

    Los mensajes de estado de la aplicación se han centralizado en un componente
    único con tres variantes: error, advertencia y confirmación. Definir el
    componente una sola vez garantiza que todos los avisos de la aplicación
    compartan apariencia y comportamiento, y que cualquier modificación futura
    se propague automáticamente a todas las pantallas que lo emplean. Su diseño
    se ha planteado teniendo en cuenta que el módulo de corrección postural
    necesitará mostrar las correcciones detectadas empleando precisamente esos
    tres niveles de gravedad.

    De forma análoga, los estilos comunes a los formularios (campos, etiquetas,
    ayudas, mensajes de error y botones) se han definido a nivel global a partir
    de las variables del sistema de diseño, de modo que las pantallas de
    registro, inicio de sesión y perfil comparten una presentación idéntica sin
    duplicar declaraciones.

    \section{Catálogo de ejercicios}

    El segundo módulo implementado es el catálogo de ejercicios, que da soporte
    a los requisitos RF-02, RF-03 y RF-04. Su desarrollo abarca desde el modelo
    de dominio y la consulta de filtrado en el servidor hasta las vistas de
    listado y detalle en el cliente.

    \subsection{Modelo de dominio y carga inicial del catálogo}

    La entidad \texttt{Exercise}, cuyos atributos se recogieron en la
    Tabla~\ref{tab:entidad-exercise}, se mapea a la tabla \texttt{exercises}.
    Los grupos musculares y los consejos de ejecución se declaran como
    colecciones de elementos mediante la anotación
    \texttt{@ElementCollection}, que genera automáticamente las tablas
    \texttt{exercise\_muscle\_groups} y \texttt{exercise\_tips} sin necesidad
    de definir entidades intermedias.

    La estrategia de carga de ambas colecciones es distinta y responde al uso
    que hace de ellas la interfaz. Los grupos musculares se recuperan de forma
    anticipada, ya que sus distintivos aparecen en todas las tarjetas del
    listado y una carga diferida provocaría un error al construir el objeto de
    transferencia fuera de la transacción. Para evitar que esa carga anticipada
    genere una consulta por cada ejercicio, problema conocido como
    \textit{N+1}, se emplea la anotación \texttt{@BatchSize}, que agrupa la
    recuperación de los grupos de varios ejercicios en una única consulta. Los
    consejos, en cambio, se cargan de forma diferida porque solo se necesitan
    en la vista de detalle, y se anotan con \texttt{@OrderColumn} para
    garantizar que se muestren siempre en el mismo orden, ya que una lista sin
    esta anotación no preserva el orden al recuperarse de la base de datos.

    Tras el primer arranque se verificó en MySQL la creación de las tres
    tablas con las columnas y claves ajenas esperadas
    (Figura~\ref{fig:tabla-exercise-creacion}), siguiendo el mismo
    procedimiento aplicado a la tabla de usuarios.

    \begin{figure}[htbp]
        \centering
        \includegraphics[width=0.85\textwidth]{img/tabla-exercise-creacion.png}
        \caption{Estructura de las tablas del catálogo generadas por Hibernate,

    El catálogo se puebla con un conjunto inicial de diez ejercicios. Para ello

    primero es que los datos se reparten en tres tablas relacionadas, de modo
    que insertarlos mediante sentencias SQL obligaría a gestionar manualmente
    las claves ajenas. El segundo, más determinante, es que la estrategia de
    generación del esquema empleada ejecutaría dicho guion en cada arranque de
    la aplicación, duplicando los registros. En su lugar se ha implementado un
    componente que se ejecuta al iniciar la aplicación y que comprueba
    previamente si el catálogo contiene ya algún ejercicio; solo si está vacío

    \subsection{Consulta de filtrado y paginación}

    El listado de ejercicios admite tres criterios de filtrado independientes y
    opcionales, lo que plantea el problema de cómo construir una consulta que
    contemple todas sus combinaciones. Las soluciones habituales consisten en
    incorporar condiciones que comprueben si cada parámetro es nulo, o en
    construir la consulta dinámicamente concatenando fragmentos de texto. La
    primera produce consultas difíciles de leer y mantener; la segunda,
    consultas que no pueden validarse en tiempo de compilación.

    Se ha optado por un enfoque distinto: ausencia de filtro se traduce en
    filtrado por todos los valores posibles. Si el usuario no selecciona
    ninguna dificultad, la capa de servicio transmite las tres a la consulta;
    si no selecciona ningún grupo muscular, transmite los ocho; y si no
    introduce texto de búsqueda, transmite una cadena vacía, que al emplearse
    en una comparación por contenido coincide con todos los nombres. La
    consulta resultante es única, fija y sin ramificaciones, y devuelve
    exactamente el mismo resultado que las alternativas descritas.

    La consulta requiere además dos precauciones derivadas de la relación con
    los grupos musculares. La primera es la eliminación de duplicados: al
    combinar la tabla de ejercicios con la de grupos, un ejercicio que trabaje
    dos de los grupos seleccionados aparecería repetido en el resultado. La
    segunda afecta al recuento total de elementos, que debe declararse de forma
    explícita; la consulta de recuento que el marco de trabajo genera por
    defecto contabilizaría esas filas duplicadas y el número de resultados
    mostrado al usuario sería incorrecto.

    Por último, la capa de servicio impone un orden por nombre cuando la
    petición no especifica otro. En una consulta paginada el orden no es una
    cuestión estética: sin una ordenación estable, la base de datos no
    garantiza que dos peticiones consecutivas devuelvan las filas en la misma
    secuencia, de modo que un mismo ejercicio podría aparecer en dos páginas
    distintas o no aparecer en ninguna.

    \subsection{Objetos de transferencia y etiquetas de presentación}

    La API no expone las entidades directamente, sino objetos de transferencia
    específicos para cada vista: uno reducido para las tarjetas del listado y
    otro completo, con la descripción y los consejos, para el detalle. Ambos se
    construyen mediante una clase de conversión que centraliza también la
    composición de la dirección de la miniatura a partir del identificador del
    vídeo.

    Los valores enumerados no se transmiten como una cadena simple, sino como
    un par formado por el identificador técnico y la etiqueta en castellano.
    Así, el grupo muscular de los glúteos viaja al cliente acompañado del texto
    que debe mostrarse. El cliente utiliza el identificador para construir las
    peticiones de filtrado y la etiqueta para representarlo en pantalla, sin
    necesidad de mantener su propia tabla de traducciones. Esta decisión evita
    que un cambio en los textos visibles, o la incorporación de un nuevo grupo
    muscular, obligue a modificar de forma coordinada el servidor y el cliente.

    Los objetos de transferencia incluyen ya los campos correspondientes a la
    valoración media, el número de valoraciones y la condición de favorito, que
    en esta fase se devolvían con valores neutros. Anticiparlos permitió que los
    componentes de la interfaz quedaran construidos en su forma definitiva y que
    la posterior incorporación de dichas funcionalidades no exigiera modificar el
    contrato de la API ni los componentes ya desarrollados.

    En el cliente, el catálogo se apoya en dos componentes reutilizables: la
    tarjeta de ejercicio y la barra de filtros, ambos concebidos para emplearse
    también en la vista de ejercicios favoritos. La página se limita a
    coordinarlos y a gestionar la comunicación con la API. La
    Figura~\ref{fig:catalogo-implementado} muestra el resultado.

    \begin{figure}[htbp]
        \centering
        \includegraphics[width=\textwidth]{img/catalogo-implementado.png}
        \caption{Vista de catálogo con el conjunto completo de ejercicios.}

    El comportamiento de la búsqueda por texto requirió dos ajustes en el
    tratamiento de las peticiones. El primero es la introducción de un retardo
    entre la última pulsación de tecla y el envío de la consulta: sin él, cada
    carácter escrito generaría una petición al servidor, de modo que buscar una
    palabra de diez letras produciría diez consultas de las que solo la última
    resulta útil. El segundo es la cancelación de las peticiones que quedan
    obsoletas. Cuando el usuario modifica los criterios antes de que se haya
    recibido la respuesta anterior, ambas peticiones quedan en curso
    simultáneamente y nada garantiza que respondan en el mismo orden en que se
    enviaron; si la más antigua llegase en último lugar, sobrescribiría unos
    resultados más recientes y la interfaz mostraría un listado que no
    corresponde a los filtros seleccionados. El operador empleado descarta
    automáticamente la petición en curso al recibir un criterio nuevo.

    Los criterios de filtrado se reflejan además en los parámetros de consulta
    de la dirección del navegador. Esto proporciona tres ventajas: la búsqueda
    puede compartirse mediante un enlace, se conserva al recargar la página y,
    sobre todo, sobrevive a la navegación hacia el detalle de un ejercicio y de
    vuelta al listado. Los valores recibidos por esta vía se contrastan con los
    admitidos antes de emplearse, de modo que una dirección manipulada
    manualmente no llega a generar una petición no válida al servidor. La
    Figura~\ref{fig:catalogo-filtrado} muestra el catálogo con varios filtros
    activos y su reflejo en la dirección.

   \section{Valoraciones y favoritos}

    El tercer módulo implementado da soporte a los requisitos RF-05, RF-06 y
    RF-07 e introduce una diferencia respecto a los anteriores: hasta ahora los
    datos eran o bien propios de un usuario o bien comunes a todos, mientras que
    aquí cada dato pertenece a un usuario concreto pero se muestra a los demás.
    Esta condición atraviesa todo el módulo y explica buena parte de las
    decisiones que se detallan a continuación.

    \subsection{Reestructuración previa de los paquetes}

    Antes de abordar la funcionalidad se unificó la organización del código del
    servidor. Los dos incrementos anteriores habían dejado dos criterios
    simultáneos ---la mayoría de las clases agrupadas por capa (modelo,
    repositorio, servicio, controlador) y las del catálogo agrupadas por
    funcionalidad---, lo que obligaba a conocer el historial del proyecto para
    saber dónde buscar una clase. Se optó por la organización por capas, que era
    la predominante, repartiendo las clases del catálogo entre los paquetes
    correspondientes y añadiendo dos paquetes para los conversores y las
    excepciones de dominio. La Tabla~\ref{tab:paquetes} recoge la estructura
    resultante. Al tratarse de una reorganización que solo cambia declaraciones
    de paquete e importaciones, sin alterar la lógica ni el nombre de las tablas
    ---fijado por la anotación \texttt{@Table} y no por la ubicación del
    código---, se registró como un cambio independiente del resto del incremento.

    \subsection{Modelo de dominio y persistencia}

    Las entidades \texttt{Review} y \texttt{Favorite}, cuyos atributos se
    recogieron en las Tablas~\ref{tab:entidad-review}
    y~\ref{tab:entidad-favorite}, se relacionan con \texttt{User} y con
    \texttt{Exercise} mediante asociaciones de muchos a uno con carga diferida
    (la fila asociada se recupera solo cuando se necesita). Ninguna de las dos
    entidades del otro extremo declara la colección inversa: hacerlo induciría a
    recorrer todas las valoraciones de un ejercicio para calcular su media, con
    el consiguiente coste.

    La regla de una sola valoración o favorito por usuario y ejercicio (RN-01 y
    RN-05) se declara mediante una restricción de unicidad sobre el par de claves
    ajenas. Esta garantía no sustituye a la comprobación previa del servicio,
    sino que la respalda: la comprobación permite responder con un mensaje
    comprensible en el caso habitual, mientras que la restricción de la tabla
    cubre el escenario en que dos peticiones simultáneas la superen ambas antes
    de que ninguna haya guardado. Las marcas temporales se asignan de forma
    centralizada en una utilidad común, tras detectarse que las entidades
    anteriores no eran consistentes en la zona horaria empleada, lo que habría
    hecho incomparables las fechas al desplegar en máquinas distintas.

    \subsection{Registro y modificación de la valoración}

    El registro se resuelve con un único procedimiento que localiza la valoración
    del usuario sobre el ejercicio y, si existe, reutiliza la fila modificando sus
    valores; si no, crea una nueva. No hay por tanto ninguna comprobación que
    rechace una segunda valoración: la regla RN-01 se cumple porque el código no
    dispone de ninguna vía para crearla, y publicar por primera vez y editar son
    literalmente la misma operación, lo que permitió incorporar la edición sin
    escribir código adicional en el servidor. Esto se apoya en el diseño de la API
    (Sección~\ref{sec:api-social}): al identificarse el recurso como la valoración
    propia sobre un ejercicio, y no mediante un identificador de valoración, la
    operación resulta idempotente ---repetirla no cambia el resultado--- y la
    identidad del autor procede siempre del token. El comentario se normaliza
    antes de guardarse: una cadena vacía o de solo espacios se almacena como nula,
    de modo que puntuar sin comentar no genera una entrada en blanco en el listado
    (RN-03).

    \subsection{Consultas de lectura: media, distribución y comentarios}

    Tres consultas de lectura sostienen la pestaña de valoraciones, y las tres
    comparten un mismo cuidado: evitar el problema \textit{N+1} descrito en el
    catálogo, esto es, una consulta adicional por cada elemento del listado.

    Conforme a la regla RN-06, la media no se almacena y se calcula en cada
    consulta. En lugar de pedirla ejercicio a ejercicio, se emplea una única
    consulta agregada que recibe los identificadores de la página y devuelve,
    agrupados por ejercicio, su media y su número de valoraciones. Esto obliga a
    contemplar dos situaciones implícitas: un ejercicio sin valoraciones no
    aparece en el resultado ---su ausencia se interpreta como media y recuento
    nulos, que la interfaz muestra como «Sin valoraciones»--- y una consulta con
    una lista de identificadores vacía no es SQL válido, por lo que el servicio
    evita lanzarla. La distribución de la vista de detalle se obtiene con una
    consulta análoga agrupada por puntuación, completando con cero los niveles que
    nadie ha seleccionado; de ella se deriva la media como media ponderada, lo que
    ahorra un acceso y garantiza que el número y las barras no se contradigan.

    El listado de comentarios se obtiene con una consulta paginada que descarta
    las valoraciones sin texto (computan en la media pero no son comentarios),
    excluye la del propio usuario ---la interfaz la muestra destacada al inicio---
    y ordena por fecha de publicación y no de modificación, de modo que corregir
    un comentario antiguo no lo desplace al primer puesto. Recupera además de
    forma anticipada el autor de cada comentario para no incurrir en una consulta
    por fila: es la tercera manifestación del problema \textit{N+1} en el módulo,
    resuelta con una tercera técnica distinta, lo que ilustra que la solución
    depende de la naturaleza del dato que falta.

    \subsection{Marcado de ejercicios favoritos}

    Las dos operaciones sobre el favorito son idempotentes: marcar uno ya marcado,
    o retirar uno que no lo estaba, se completa sin efecto ni error. El listado de
    favoritos reúne los ejercicios con sus marcas y los ordena por la fecha en que
    se guardaron ---atributo cuya existencia justifica que la relación se modelase
    como entidad y no como una simple relación de muchos a muchos---. Para saber
    qué ejercicios de una página son favoritos se usa, como con las valoraciones,
    una única consulta que devuelve solo los identificadores marcados. Como
    consecuencia, el listado del catálogo, que combina datos de tres tablas, se
    resuelve con un número constante de consultas, y la vista de favoritos no es
    una vista nueva sino ese mismo listado con un origen de datos distinto.

    \subsection{Control de acceso a las operaciones sociales}

    Ninguna clase del módulo contiene comprobaciones de autenticación: la
    protección procede de la configuración de Spring Security del primer
    incremento, que exige un token válido en toda ruta que no sea de
    autenticación, de modo que las rutas nuevas quedaron protegidas sin tocarla.
    La identidad del usuario se toma siempre del contexto de seguridad ---nunca
    del cuerpo de la petición ni de la ruta---, lo que produce una propiedad
    relevante: como ninguna ruta acepta el identificador de una valoración sino el
    del ejercicio, la búsqueda se realiza siempre por la pareja ejercicio--usuario
    y solo puede encontrar valoraciones propias. La regla RN-04 no se sostiene por
    tanto sobre una comprobación que pudiera omitirse, sino sobre la imposibilidad
    de expresar la petición. En el cliente, el contenido de los comentarios ---que
    redacta un usuario y se muestra a los demás--- se representa mediante
    interpolación, que en Angular escapa el texto por defecto y evita así un
    ataque de \textit{cross-site scripting} (la inyección de código a través del
    contenido que introduce un usuario); se evita deliberadamente el enlace a
    \texttt{innerHTML}, que sí lo interpretaría.

    \subsection{La interfaz de valoraciones}

    La puntuación mediante estrellas aparece en la tarjeta del catálogo, la
    cabecera del detalle y cada comentario, además del formulario, donde debe
    admitir interacción; se implementó por ello como un componente propio con tres
    modos (lectura, selección y selección bloqueada) y tres tamaños. Para
    representar medias decimales, en lugar de recurrir a media estrella se
    superponen dos filas de cinco estrellas ---una neutra y otra de acento cuya
    anchura se recorta en proporción al valor---, de modo que una media de 4,2
    equivale a un 84\,\% de anchura. Las fechas se muestran en términos relativos
    mediante la internacionalización que ofrece el propio navegador, evitando una
    biblioteca adicional.

    La pestaña completa requiere dos peticiones ---el resumen y la primera página
    de comentarios---, que se lanzan solo al abrirla y de forma simultánea. Tras
    publicar, modificar o eliminar una valoración se recargan ambas en lugar de
    actualizar el estado local con la respuesta: aunque supone dos accesos, la
    operación afecta a la vez a la media, la distribución, el recuento y la
    composición del listado, y reproducir esas transformaciones en el cliente
    duplicaría reglas del servidor y abriría la puerta a discrepancias entre lo
    mostrado y lo almacenado. El estado se reinicia al navegar de un ejercicio a
    otro, ya que el marco de trabajo reutiliza la misma instancia del componente
    y, sin ese reinicio, se mostrarían un instante las valoraciones del anterior.

    \subsection{Un efecto colateral entre la reactividad y el DOM}

    La incorporación del botón de favorito a la vista de detalle produjo un
    comportamiento inesperado: tras pulsarlo, el control de retroceso del navegador
    exigía dos pulsaciones y el vídeo embebido se reiniciaba. El origen estaba tres
    pasos por delante del síntoma. Al cambiar la condición de favorito se sustituye
    el objeto que representa el ejercicio, como exige el modelo reactivo basado en
    señales, que detecta los cambios comparando referencias; esa sustitución
    recalculaba el valor derivado que compone la dirección del vídeo, la cual debe
    declararse como segura y devuelve una instancia distinta en cada invocación
    aunque el identificador sea el mismo, de modo que el marco flotante se
    recargaba y añadía una entrada al historial del navegador. La corrección
    consistió en interponer un valor derivado intermedio que expone solo el
    identificador del vídeo: al ser una cadena de texto, su comparación por
    igualdad detiene la propagación antes de recalcular la dirección. Es un patrón
    general: cuando un cálculo costoso depende de un objeto que se sustituye por
    motivos ajenos a él, conviene intercalar un valor derivado con el dato mínimo
    del que realmente depende.

    \subsection{Consolidación técnica al cierre del incremento}

    Antes de cerrar el incremento se abordó un conjunto de mejoras de coherencia
    interna acumuladas durante el desarrollo y registradas como tareas a medida
    que se detectaban, criterio que evita tanto interrumpir cada funcionalidad
    para corregir un detalle como dejar que se conviertan en deuda técnica. En el
    servidor se unificaron la obtención de marcas temporales, el formato de las
    respuestas de error y el estilo de inyección de dependencias, y se pasó a
    responder \texttt{401} ante un token que identifica a un usuario inexistente;
    en el cliente se extrajo a configuración la dirección base de la API, se
    incorporaron al sistema de diseño las clases repetidas y se registró la
    configuración regional española, sin la cual la media se mostraba con
    separador decimal anglosajón. No todo se resolvió: se descartaron de forma
    razonada, por exceder su coste al beneficio con el volumen de datos previsto,
    la paginación del listado de favoritos y la inclusión del identificador de
    usuario en el token, entre otras, cuyo registro explícito permite distinguir
    la deuda técnica asumida de la que responde a un descuido.


    \section{Módulo de corrección postural}

    La implementación del módulo de corrección postural materializa el diseño
    descrito en el Capítulo~\ref{cap:diseno}. A diferencia de los módulos
    anteriores, su lógica reside casi por completo en el cliente: el vídeo, la
    estimación de pose y el cálculo de la puntuación se resuelven en el navegador,
    y el servidor interviene únicamente para persistir el resultado. Esta sección
    describe la construcción de esa cadena de procesamiento, desde la lectura del
    vídeo hasta la generación del \textit{feedback}.

    \subsection{Estimación de pose con MediaPipe}

    El punto de partida es la carga del vídeo. El usuario selecciona un archivo
    local que se reproduce en el navegador mediante una dirección de tipo
    \texttt{blob}, generada por el propio navegador y que apunta a un contenido
    que reside únicamente en memoria. Como ocurría con el vídeo embebido de
    YouTube, el marco de trabajo bloquea por seguridad la asignación dinámica de
    esta dirección, por lo que debe declararse explícitamente como segura. La
    diferencia con aquel caso es instructiva: allí la dirección se componía a
    partir de un identificador procedente de la base de datos, mientras que aquí
    la acuña el navegador a partir del archivo elegido, sin intervenir dato alguno
    manipulable. Al descartar el vídeo o cargar otro, la dirección se libera
    explícitamente para no retener el contenido en memoria, precaución que con
    archivos de vídeo resulta especialmente relevante.

    Sobre el vídeo en reproducción opera el modelo de estimación de pose. El
    componente inicializa el \texttt{PoseLandmarker} en modo vídeo y recorre la
    reproducción mediante el ciclo de refresco del navegador, entregando cada
    fotograma al modelo y acumulando los puntos detectados. El análisis se
    resuelve al finalizar la reproducción y no durante ella, ya que la puntuación
    de un ejercicio dinámico requiere disponer de todas sus repeticiones antes de
    poder emitirse.

    La integración del modelo en modo vídeo reveló la incidencia más
    característica de este módulo, relacionada con la marca temporal que debe
    acompañar a cada fotograma. El modelo exige que esa marca sea estrictamente
    creciente entre llamadas sucesivas; de no serlo, su grafo de cómputo interno
    entra en un estado de error del que no se recupera. La primera aproximación,
    derivar la marca del instante de reproducción del vídeo, resultó ser el error
    de fondo: dicho instante puede repetirse entre dos fotogramas consecutivos,
    retroceder si el usuario rebobina y reiniciarse a cero al cargar un vídeo
    nuevo, y cualquiera de esas tres situaciones interrumpía el análisis. La
    solución no consistió en corregir el cálculo de esa marca, sino en
    desacoplarla por completo del vídeo: se emplea un reloj monótono global,
    independiente de la reproducción, que por construcción nunca retrocede ni se
    reinicia, mientras que el instante del vídeo se reserva únicamente para
    detectar si un fotograma es nuevo. Este caso ilustra que un síntoma
    aparentemente puntual, un fallo intermitente en cierto fotograma, puede
    responder a una decisión conceptual equivocada, y que su resolución pasa por
    replantear el enfoque y no por acumular correcciones sobre él.

    Los puntos detectados se representan sobre el vídeo mediante un lienzo
    (\textit{canvas}) superpuesto, que dibuja el esqueleto en tiempo real
    conforme avanza la reproducción. La correcta superposición exige que el
    lienzo se dimensione según la resolución real del vídeo, y no según su tamaño
    de representación en pantalla, dado que los puntos se expresan en coordenadas
    normalizadas que deben proyectarse sobre las dimensiones nativas de la imagen;
    un dimensionado incorrecto desplaza el esqueleto respecto al cuerpo.

    \begin{figure}[htbp]
        \centering
        \includegraphics[width=\textwidth]{img/analisis-esqueleto.png}
        \caption{Esqueleto detectado superpuesto sobre el vídeo durante el
        análisis.}
        \label{fig:analisis-esqueleto}
    \end{figure}

    Junto al esqueleto, la interfaz muestra bajo el vídeo un panel de métricas en
    tiempo real que expone los ángulos relevantes del ejercicio en curso ---la
    rodilla y la inclinación del tronco en la sentadilla, la cadera y el cuello
    en la plancha, y las magnitudes correspondientes en los demás---. Cada valor
    se colorea en verde o rojo según cumpla o no el mismo umbral que emplea la
    evaluación, de modo que la retroalimentación instantánea es coherente con la
    puntuación final. Este panel sustituyó a una etiqueta que se superponía sobre
    el vídeo en una versión anterior: al ocupar un espacio propio deja de tapar
    la imagen del cuerpo, permite mostrar varias métricas a la vez y, al derivar
    su color de los umbrales reales, sirve también como ayuda para el ajuste
    empírico de dichos umbrales.

    \subsection{Cálculo de métricas: ángulos articulares y alineaciones}

    Con los puntos de cada fotograma disponibles, el cálculo de las métricas se
    resuelve mediante la función de ángulo de tres puntos descrita en el diseño,
    implementada como una función pura que opera sobre coordenadas ya corregidas
    en su relación de aspecto. Su carácter autónomo y determinista la hizo
    idónea como primera pieza del proyecto cubierta por pruebas unitarias
    automatizadas.

    Antes de calcular ángulo alguno, el sistema decide qué costado del cuerpo
    analizar. En una grabación de perfil, uno de los dos lados queda parcialmente
    oculto, y sus puntos se detectan con menor confianza. En lugar de fijar un
    lado de antemano, el módulo compara la confianza acumulada de ambos costados
    a lo largo de todo el vídeo y selecciona el más visible, decisión que se toma
    una sola vez por análisis para no alternar de lado a mitad de la ejecución.
    Con el costado ya elegido, se descartan además los fotogramas en que los
    puntos clave de la articulación evaluada presentan baja confianza, de manera
    que la señal de ángulos sobre la que se detectan las repeticiones y se
    aplican las reglas queda depurada de las observaciones menos fiables.

    Este filtrado tiene una consecuencia que conviene notar: la señal resultante
    deja de ser temporalmente continua, al haberse eliminado fotogramas
    intermedios. No obstante, la detección de repeticiones no depende de la
    continuidad temporal sino de la forma de la señal, la sucesión de descensos
    y ascensos del ángulo, por lo que la ausencia de algunos fotogramas no la
    afecta. La mejora de fiabilidad que aporta descartar los datos dudosos
    compensa con holgura esa pérdida de continuidad, y constituye un ejemplo del
    principio de cuidar la calidad de los datos de entrada antes de complicar el
    algoritmo que los procesa.

    \subsection{Detección de repeticiones y extracción de muestras}

    La etapa que distingue a un ejercicio dinámico de uno estático es la
    extracción de muestras: la forma en que la señal continua de ángulos se
    convierte en las observaciones concretas sobre las que se aplican las reglas.
    En la plancha, estática, cada fotograma es ya una muestra válida. En la
    sentadilla ---y, análogamente, en la zancada y la flexión--- hace falta antes
    identificar las repeticiones, pues la técnica se juzga en instantes concretos
    de cada una, como la profundidad en el punto más bajo.

    Contar repeticiones equivale a localizar los mínimos de la señal del ángulo de
    rodilla: cada repetición es un descenso seguido de un ascenso. El problema es
    que esa señal no es limpia. Presenta pequeñas oscilaciones procedentes tanto
    del movimiento real como de la imprecisión de la estimación de pose, de modo
    que una búsqueda ingenua de mínimos contabilizaría repeticiones inexistentes
    ante cualquier temblor. La detección se apoya por ello en dos mecanismos
    (Figura~\ref{fig:deteccion-repeticiones}).

    El primero es un \textbf{suavizado} previo de la señal mediante una media
    móvil, que promedia cada valor con sus vecinos y atenúa el ruido de alta
    frecuencia sin desdibujar la forma general del movimiento. El segundo es una
    \textbf{banda de histéresis}: en lugar de un único umbral que separe la
    posición alta de la baja, se emplean dos, uno para dar por comenzada una
    repetición y otro, más alto, para darla por concluida. El comportamiento es
    análogo al de un termostato, que enciende y apaga a temperaturas distintas
    para no oscilar sin fin en torno a un único valor: la franja comprendida entre
    ambos umbrales actúa como zona muerta e impide que una vacilación del ángulo
    alrededor de un mismo valor se contabilice como varias repeticiones.

    Conviene subrayar que estos umbrales de detección son independientes de los
    que evalúan la técnica: los primeros determinan \emph{qué constituye una
    repetición} y los segundos, \emph{si esa repetición es correcta}. Una vez
    delimitada cada repetición, el analizador toma de ella una única muestra en el
    instante relevante ---el de mayor flexión, para la profundidad---, y es sobre
    ese conjunto de muestras, y no sobre todos los fotogramas, sobre el que opera
    después el motor de puntuación.

    \subsection{Generación del feedback y la puntuación}

    La puntuación se calcula mediante el motor de reglas común descrito en el
    diseño. Cada regla se implementa como una estructura de datos que declara la
    condición que comprueba, el mensaje de corrección asociado y su penalización
    máxima, de modo que el motor es genérico y las reglas de cada ejercicio se
    reducen a una tabla que aquel interpreta. Esta separación permitió que la
    incorporación del analizador de la plancha, una vez construido el de la
    sentadilla, no requiriese modificar el motor: bastó con definir sus reglas y
    su forma de extracción de muestras.

    El analizador de la sentadilla extrae una muestra por repetición, conforme a
    la detección descrita en el apartado anterior, mientras que el de la plancha
    trata cada fotograma como una muestra. La regla de
    estabilidad de la plancha, que evalúa la serie temporal completa en lugar de
    una muestra aislada, se integra como una penalización adicional que el motor
    incorpora al cómputo global sin alterar la condición de que el total sume
    cien. El resultado se distingue según el tipo de ejercicio: en la sentadilla,
    cada corrección indica en cuántas repeticiones se ha incumplido la regla; en
    la plancha, esa cuenta por repeticiones carece de sentido y se omite. Es un
    caso de un mismo dato presentado de forma distinta según el contexto, en el
    que la lógica produce la información y la interfaz decide cómo mostrarla.

    El módulo se niega a emitir una puntuación cuando no dispone de datos
    fiables: si no se detecta ninguna repetición completa, o si ningún fotograma
    supera el umbral de confianza, no se inventa una nota, sino que se informa al
    usuario de que la grabación no reúne las condiciones necesarias. Esta cautela
    es coherente con la naturaleza orientativa de la herramienta: una puntuación
    espuria derivada de una grabación deficiente resultaría más perjudicial que
    la ausencia de puntuación.

    La interfaz del módulo se organiza como una máquina de estados de tres fases,
    selección del vídeo, análisis y resultado, cada una con su
    representación propia. La vista de resultado reproduce la maqueta diseñada:
    un indicador circular con la puntuación, coloreado según los umbrales de
    valoración, y la relación de correcciones, cada una con su gravedad y, cuando
    procede, el valor medido frente al esperado. Las reglas satisfechas se
    muestran también, en positivo, de modo que el usuario reciba una devolución
    equilibrada y no únicamente la relación de errores.

    \begin{figure}[htbp]
        \centering
        \includegraphics[width=\textwidth]{img/analisis-resultados.png}
        \caption{Vista de resultados del análisis en la aplicación, con la
        puntuación coloreada y las correcciones detectadas.}
        \label{fig:analisis-resultados}

    Se descartó deliberadamente una funcionalidad presente en la maqueta: el
    enlace desde cada corrección al instante exacto del vídeo en que se detecta.
    Su implementación exigiría conservar, junto a cada corrección, la marca
    temporal del fotograma que la origina, dato que solo tiene sentido mientras el
    vídeo permanece cargado en el navegador. Dado que el vídeo no se persiste,
    conforme al requisito RNF-02, dicho enlace quedaría sin destino una vez
    recuperado el análisis del historial, por lo que se pospone como línea de
    trabajo futuro.

    \subsection{Ajuste empírico de los umbrales}

    Los umbrales concretos de cada regla ---la profundidad que se considera
    suficiente, la inclinación de tronco admisible o el margen de alineación de la
    plancha--- parten de los valores tomados de la literatura biomecánica, pero su
    valor final se afinó de forma empírica sobre grabaciones de prueba. El panel de
    métricas en tiempo real descrito más arriba resultó decisivo para ello: al
    mostrar, fotograma a fotograma, el valor medido junto al color que indica si
    supera o no el umbral vigente, permitió contrastar ejecuciones correctas e
    intencionadamente incorrectas y comprobar que cada umbral separa unas de otras
    sin marcar como error una técnica válida ni pasar por alto una deficiente. Los
    ajustes se limitaron a estrechar o ampliar ligeramente los márgenes de
    tolerancia; los criterios de fondo, y su respaldo en la literatura, se
    mantuvieron inalterados. Se trata de un ajuste orientado a la coherencia de la
    herramienta, no de una calibración clínica, en consonancia con el carácter
    orientativo del sistema.

    \subsection{Persistencia del resultado y página de inicio}

    Al concluir un análisis válido, su resultado se envía al servidor para
    incorporarse al historial. Este envío se realiza en segundo plano y sin
    bloquear la interfaz: el usuario visualiza su puntuación de inmediato, con
    independencia de que la persistencia llegue a completarse. Si la comunicación
    con el servidor falla, el análisis se ha mostrado igualmente y solo se pierde
    su registro en el historial, consecuencia asumible dado que el objetivo
    principal, evaluar la técnica, se cumple en el cliente. Únicamente se
    persisten los análisis que han producido una puntuación, de modo que una
    grabación que el módulo rechaza no genera entrada alguna.

    En el servidor, la entidad \texttt{AnalysisResult} y sus operaciones siguen
    la misma arquitectura por capas del resto del sistema. El historial se
    recupera mediante una consulta que reúne cada resultado con su ejercicio en
    un único acceso, evitando el problema \textit{N+1} descrito en los módulos
    anteriores. El resumen de la página de inicio se resuelve, conforme al
    diseño, con dos consultas de recuento independientes.

    \section{Contenerización con Docker}

Los incrementos anteriores se desarrollaron con la base de datos en un
    contenedor Docker mientras el backend y el frontend se ejecutaban
    directamente sobre la máquina de desarrollo. El incremento de cierre aborda
    el empaquetado completo del sistema, de modo que los tres componentes
    —base de datos, servidor y cliente— se construyan y ejecuten como
    contenedores coordinados por una única definición. El objetivo es el que
    fija el requisito RNF-05: que el sistema completo pueda desplegarse en
    cualquier máquina con Docker sin instalaciones ni configuraciones manuales,
    garantizando un entorno reproducible.

    \subsection{Imágenes del backend y del frontend}

    Cada componente se empaqueta mediante una imagen construida en dos etapas
    (\textit{multi-stage build}), técnica que separa la fase de compilación de
    la de ejecución para que la imagen final contenga únicamente lo
    imprescindible para funcionar.

    En el backend, la primera etapa parte de una imagen con Maven y el JDK,
    compila el proyecto y produce el archivo \texttt{.jar} ejecutable; la
    segunda parte de una imagen mínima con solo el entorno de ejecución de Java,
    a la que se copia dicho archivo. Así, la imagen resultante no arrastra ni el
    compilador ni el código fuente, lo que reduce su tamaño y su superficie de
    exposición; por seguridad, el proceso se ejecuta además con un usuario sin
    privilegios.

    En el frontend se sigue el mismo principio: una primera etapa con Node
    compila la aplicación de Angular y genera los ficheros estáticos
    optimizados, que una segunda etapa sirve mediante un servidor web ligero.
    Entre los ficheros servidos se incluyen los del motor de MediaPipe y el
    modelo de estimación de pose, alojados en la propia aplicación, lo que
    mantiene la ausencia de dependencias de red en tiempo de ejecución exigida
    por el diseño.

    \subsection{Orquestación con Docker Compose}

    La puesta en marcha conjunta de los tres contenedores se describe en un
    fichero de Docker Compose~\cite{dockercompose} que declara los servicios, la red interna que los
    comunica y los volúmenes que preservan los datos. El backend se comunica con
    la base de datos a través del nombre del servicio dentro de la red interna
    de Docker, y no mediante una dirección fija; por ello, los parámetros de
    conexión se proporcionan como variables de entorno en lugar de fijarse en el
    código, lo que permite que la misma imagen funcione sin cambios tanto en
    desarrollo como en el despliegue.

    Los datos sensibles la contraseña de la base de datos y la clave de firma
    de los tokens se externalizan a un fichero de entorno que queda fuera del
    control de versiones, acompañado de una plantilla de ejemplo que documenta
    las variables necesarias sin exponer ningún valor real.

    El arranque se coordina mediante una comprobación de salud
    (\textit{healthcheck}) sobre la base de datos: el servidor no inicia hasta
    que MySQL está realmente listo para aceptar conexiones, lo que evita los
    fallos propios de un arranque simultáneo. Al levantarse sobre una base de
    datos vacía, el catálogo inicial se carga de forma automática mediante el
    mecanismo idempotente descrito con anterioridad, de modo que un despliegue
    nuevo queda operativo con los ejercicios disponibles y sin datos de usuario
    previos.

    \subsection{Punto de entrada único y proxy inverso}

    El servidor web que sirve el frontend, Caddy~\cite{caddy}, actúa además como proxy inverso:
    atiende todas las peticiones del cliente y reenvía al backend aquellas
    dirigidas a la ruta \texttt{/api}, mientras entrega el resto como parte de
    la aplicación de Angular. Esta disposición ofrece dos ventajas. La primera
    es que cliente y API quedan expuestos bajo un mismo origen, lo que elimina
    en el despliegue la necesidad de la configuración de CORS descrita en el
    Capítulo~\ref{cap:implementacion}, propia únicamente del entorno de
    desarrollo, en el que cliente y servidor se sirven en puertos distintos. La
    segunda es la gestión automática del cifrado: al indicarle un nombre de
    dominio, el proxy obtiene y renueva por sí mismo el certificado necesario
    para servir la aplicación sobre HTTPS, sin intervención manual. En
    desarrollo local, en ausencia de dominio, el mismo componente sirve la
    aplicación sobre HTTP, de modo que una única configuración cubre ambos
    escenarios.

    \section{Resultados}

    El conjunto de pruebas descrito confirma que el sistema se comporta conforme
    a lo especificado en los distintos niveles de verificación. Las pruebas
    funcionales y de integración recorrieron los flujos de autenticación,
    catálogo, valoraciones y favoritos, completándose todos los casos con el
    resultado esperado, tanto en los escenarios correctos como en los de error.
    El módulo de corrección postural se validó en dos planos complementarios: las
    pruebas unitarias garantizaron la corrección del cálculo geométrico y del
    motor de puntuación, mientras que la validación sobre vídeo real confirmó que
    la evaluación discrimina entre una ejecución técnicamente correcta y otra con
    un error deliberado, y que las correcciones señaladas se corresponden con los
    errores introducidos en cada uno de los cuatro ejercicios.

    Esta misma validación delimitó de forma empírica las condiciones de uso de la
    herramienta. Las grabaciones que se apartan de la vista de perfil o de un
    rango de movimiento estándar, así como aquellas con iluminación deficiente,
    degradan la estimación de pose; en esos casos el sistema no emite una
    puntuación arbitraria, sino que rechaza la grabación o refleja la
    degradación, un comportamiento coherente con las restricciones de alcance
    declaradas en el diseño y con las recomendaciones que la propia interfaz
    ofrece al usuario. El sistema cumple, en consecuencia, los objetivos
    funcionales previstos dentro de las condiciones para las que fue concebido.

    Por último, una vez empaquetado el sistema en contenedores, el conjunto de
    funcionalidades se repasó sobre el despliegue completo en ejecución,
    manteniéndose en todos los casos el comportamiento esperado.

\section{Conclusiones}

    Este Trabajo Fin de Grado se planteó como objetivo general el desarrollo de
    una aplicación web de fitness que permitiera consultar ejercicios guiados,
    llevar un registro del entrenamiento y recibir apoyo en la corrección de la
    postura mediante técnicas de estimación de pose, con la intención de mejorar
    el entrenamiento autónomo sin sustituir la supervisión de un profesional.
    El resultado es un sistema completo y funcional que cubre ese objetivo y
    cada uno de los objetivos específicos derivados de él.

    En el plano de la gestión y la consulta, la aplicación resuelve el registro,
    la autenticación y la gestión del perfil de forma segura mediante tokens, y
    ofrece un catálogo de ejercicios con filtrado por grupo muscular y
    dificultad, una vista de detalle con descripción, consejos y vídeos
    embebidos, un sistema de valoraciones y comentarios con la puntuación
    mostrada de forma agregada, y la posibilidad de marcar ejercicios como
    favoritos. Todo ello se sostiene sobre la arquitectura cliente-servidor
    prevista, con un frontend en Angular y un backend con API REST,
    autenticación y persistencia de datos, cumpliéndose así el objetivo de
    desarrollo full-stack.

    El núcleo diferenciador del trabajo, la corrección postural asistida, se ha
    implementado evaluando la ejecución a partir de vídeos procesados
    íntegramente en el navegador, sin que el material salga del dispositivo del
    usuario. Sobre esa base, el sistema calcula para cada ejercicio las métricas
    pertinentes ---ángulos articulares y alineaciones--- y devuelve una puntuación
    global acompañada de mensajes de corrección concretos, satisfaciendo los
    objetivos de cálculo de métricas y de generación de retroalimentación.

    Más allá del cumplimiento de los objetivos, conviene destacar dos decisiones
    que definen el carácter del sistema. La primera es el enfoque del análisis:
    al basarse en reglas geométricas justificadas biomecánicamente, la
    valoración resulta transparente y explicable, en lugar de proceder de un
    modelo opaco. La segunda es su naturaleza orientativa; el sistema no emite
    una puntuación cuando los datos no son fiables y asume unas condiciones de
    grabación determinadas, de modo que sirve de apoyo al entrenamiento autónomo
    pero no reemplaza el criterio de un profesional, tal como se propuso desde el
    inicio. Finalmente, la contenerización del sistema completo garantiza que
    pueda desplegarse de forma reproducible, lo que traslada el proyecto desde el
    entorno de desarrollo hacia un despliegue real.

    La metodología incremental adoptada ha sido determinante para alcanzar este
    resultado: abordar el sistema en incrementos funcionales sucesivos permitió
    validar cada bloque antes de construir sobre él y mantener el proyecto bajo
    control en todo momento. El desarrollo ha exigido integrar tecnologías
    diversas ---desde la estimación de pose en el navegador hasta la orquestación
    de contenedores---, lo que ha supuesto el principal aprendizaje del trabajo.
    Las dificultades encontradas durante el proceso y las líneas por las que el
    sistema podría evolucionar se detallan en los apartados siguientes.

    \section{Dificultades encontradas}

    El desarrollo estuvo jalonado por diversas incidencias cuya resolución, más
    allá de desbloquear el trabajo, dejó enseñanzas de carácter general. Se
    sintetizan aquí las más representativas; su tratamiento técnico detallado se
    encuentra en el Capítulo~\ref{cap:implementacion}, donde se describen en el
    contexto en que surgieron.

    Un primer grupo tuvo su origen en los \textbf{comportamientos por omisión de
    los marcos de trabajo}. La incorporación de Spring Security dejó inicialmente
    inaccesible el registro y provocó rechazos con código \texttt{403} debidos a
    una protección concebida para formularios con sesión, ajena a una API sin
    estado; de modo análogo, la estrategia de carga diferida de datos, adecuada
    como norma general, derivó en el conocido problema de las consultas repetidas
    (\textit{N+1}). En todos los casos el síntoma resultaba desconcertante hasta
    comprender qué mecanismo estaba activo sin haberlo solicitado, lo que subraya
    la importancia de conocer las decisiones que un marco adopta por defecto.

    Un segundo grupo, propio del cliente, derivó de la \textbf{propagación
    implícita de los cambios} en el modelo reactivo basado en señales. El caso
    más ilustrativo fue un fallo en la navegación que se manifestaba tres pasos
    por delante de su causa real, al encadenarse el marcado de un favorito con la
    recarga del vídeo embebido. Este defecto, junto con otros que solo se
    revelaron al recorrer la aplicación completa como lo haría un usuario ---y no
    al probar los puntos de entrada de la API por separado---, confirmó que la
    verificación de extremo a extremo es imprescindible y complementa, sin
    sustituirla, a la prueba aislada de cada componente.

    La incidencia más instructiva del proyecto afectó al núcleo del análisis
    postural: una \textbf{marca temporal que no podía retroceder}. El modelo de
    estimación de pose exige que el instante asociado a cada fotograma crezca de
    forma estricta, y la primera aproximación ---derivarlo de la reproducción del
    vídeo--- lo incumplía al rebobinar o recargar, deteniendo el análisis de
    forma intermitente. La solución no consistió en refinar aquel cálculo, sino
    en sustituirlo por completo por un reloj independiente de la reproducción. El
    caso dejó una lección transferible: cuando un síntoma resulta especialmente
    desconcertante, a veces la vía de salida no es perfeccionar el enfoque
    vigente, sino reconocer que el propio enfoque es la causa y reemplazarlo.

    Por último, la validación sobre vídeo real puso sobre la mesa la disyuntiva
    entre \textbf{la calidad de los datos y la complejidad del algoritmo}. Ante
    el temblor de los puntos detectados y la degradación en grabaciones poco
    favorables, la tentación era sofisticar el procesamiento de la señal; la
    solución adoptada siguió el camino contrario, depurando los datos de entrada
    ---seleccionando el costado más visible y descartando los fotogramas poco
    fiables--- antes de que llegaran al algoritmo. Mejorar la entrada resultó más
    eficaz, y más simple de mantener, que complicar el procesamiento para
    absorber un ruido evitable.

    \section{Líneas de trabajo futuro}

    \subsection{Seguridad y despliegue}

    El sistema de autenticación implementado cumple su cometido. El despliegue
    en contenedores aborda ya una de las cuestiones que un uso en producción
    plantearía ---el cifrado del canal---, mientras que las restantes quedan como
    trabajo futuro.

    El cifrado del canal lo proporciona el propio despliegue: el proxy inverso
    descrito en el Capítulo~\ref{cap:implementacion} sirve la aplicación sobre
    HTTPS y renueva el certificado de forma automática. En el entorno de
    desarrollo local, en cambio, la comunicación se realiza sobre HTTP y el
    token viaja en claro; dado que un token JWT va firmado pero no cifrado,
    cualquiera que lo interceptase en ese contexto podría leer su contenido y
    reutilizarlo hasta su caducidad, circunstancia que es precisamente la razón
    por la que el token no incorpora ningún dato sensible más allá del nombre de
    usuario y su rol.

    Queda pendiente, en cambio, un mecanismo de revocación. Al no mantenerse
    ninguna sesión en el servidor, cerrar sesión se limita a eliminar el token
    del cliente, mientras que una copia sustraída seguiría siendo válida hasta
    expirar. La solución habitual combina una caducidad breve con un segundo
    token de renovación, planteamiento que excede el alcance de este trabajo.

    En cuanto a la gestión de credenciales, tanto la clave de firma de los
    tokens como la contraseña de la base de datos se proporcionan mediante
    variables de entorno, recogidas en un fichero que queda fuera del control de
    versiones, de manera que ningún secreto figure en el repositorio. Conviene
    subrayar, no obstante, que un secreto que haya llegado a registrarse en el
    historial de un sistema de control de versiones permanece accesible en él
    aunque se elimine del fichero, por lo que un despliegue real debe emplear
    credenciales nuevas y no las utilizadas durante el desarrollo.

    A ello se añade que el registro de usuarios no verifica la titularidad del
    correo electrónico. La regla que limita a una la valoración por usuario y
    ejercicio acota el efecto de una eventual creación masiva de cuentas sobre
    las valoraciones, pero no lo elimina.

    \subsection{Reconocimiento automático del ejercicio}

    El módulo de corrección postural parte de una premisa: que el vídeo aportado
    se corresponde con el ejercicio seleccionado por el usuario en el catálogo.
    El análisis extrae de la secuencia las magnitudes geométricas relevantes y
    les aplica las reglas de ese ejercicio, pero en ningún momento comprueba que
    el movimiento grabado sea realmente el esperado. Como se observó en las
    pruebas, al proporcionar el vídeo de un ejercicio distinto el sistema no lo
    rechaza, sino que lo evalúa con las métricas del ejercicio seleccionado y
    emite una puntuación ---habitualmente baja--- carente de sentido. Este
    comportamiento es coherente con la naturaleza del análisis, que mide la
    geometría del movimiento pero no clasifica el ejercicio que aparece en la
    imagen.

    Una línea natural de mejora consistiría en incorporar un reconocimiento
    automático del ejercicio, capaz de verificar que el vídeo se corresponde con
    el seleccionado o, en su defecto, de identificarlo por sí mismo. Ello
    requeriría un modelo de clasificación entrenado a tal efecto, ajeno al
    enfoque basado en reglas adoptado en este trabajo, por lo que queda fuera de
    su alcance y se plantea como trabajo futuro.

    \subsection{Evolución del módulo de valoraciones y favoritos}

    Varias decisiones de este incremento resultan adecuadas al volumen de datos
    previsto pero dejarían de serlo con un uso intensivo. El filtrado de la
    vista de favoritos se resuelve en el navegador sobre la lista ya
    descargada, lo que ofrece una respuesta inmediata mientras el número de
    ejercicios guardados sea reducido; una lista extensa exigiría trasladar el
    filtrado al servidor, reutilizando los parámetros que ya admite el
    catálogo. Del mismo modo, la vista de favoritos no incorpora paginación,
    prescindible con un catálogo de diez ejercicios pero necesaria si este
    creciera.

    Las marcas temporales se almacenan sin información de zona horaria, lo que
    resulta correcto mientras servidor y usuarios comparten la misma, pero
    impide un despliegue en varias regiones. Sustituirlas por un tipo que
    incorpore la referencia temporal absoluta resolvería la limitación y
    permitiría al cliente adaptar la representación a la zona de cada usuario.

    Por último, el módulo admite extensiones funcionales que no se han abordado
    por quedar fuera de los requisitos: la posibilidad de responder a un
    comentario, la moderación de contenido inadecuado o la ordenación del
    catálogo por valoración media, para la que el modelo de datos actual ya
    dispone de la información necesaria.

    \subsection{Deuda técnica identificada}

    El seguimiento del proyecto incorporó desde el primer incremento un
    registro explícito de mejoras técnicas detectadas durante el desarrollo
    pero no abordadas en el momento, con el fin de evitar tanto la
    interrupción constante del trabajo en curso como el olvido de las
    incidencias. La mayor parte se resolvió al cierre de cada incremento, según
    se describe en el Capítulo~\ref{cap:implementacion}; el resto permanece
    documentado y razonado.

    Entre lo pendiente destaca la extracción de los campos de auditoría de las
    entidades a una clase base común, que eliminaría la repetición de los
    métodos de asignación de marcas temporales en las entidades del
    modelo. Se pospuso por afectar simultáneamente a todas ellas en un momento
    del calendario en que la prioridad era completar la funcionalidad prevista.

    Otras decisiones se descartaron de forma razonada por resultar su coste
    superior al beneficio con el volumen de datos previsto: incorporar el
    identificador del usuario al token para evitar una consulta por petición,
    lo que acoplaría el token al modelo de datos, y reforzar el mecanismo de
    retroceso del navegador frente a interacciones del usuario con el
    reproductor de vídeo embebido. Documentar estos descartes junto a su
    justificación permite distinguir la deuda técnica asumida de forma
    deliberada de aquella que responde a un descuido.

        \umaappendix{Manual de instalación y despliegue}

        Este apéndice describe cómo poner en marcha el sistema completo, base de
        datos, servidor y cliente, en cualquier máquina, así como las
        consideraciones para un despliegue accesible desde Internet. Todo el proceso
        se apoya en la contenerización descrita en el
        Capítulo~\ref{cap:implementacion}, de modo que no requiere instalar
        manualmente ninguna de las tecnologías empleadas.
    
        \section*{Requisitos previos}
    
        El único requisito para ejecutar el sistema es tener instalado
        \textbf{Docker Desktop}, que incorpora Docker Compose. No es necesario
        instalar Java, Node, Maven ni MySQL: cada componente se construye y ejecuta
        dentro de su propio contenedor.
    
        \section*{Puesta en marcha}
    
        \begin{enumerate}
            \item Obtener el código del proyecto y situarse en la carpeta raíz, la
            que contiene el fichero \texttt{docker-compose.yml}.
    
            \item Crear el fichero de configuración \texttt{.env} a partir de la
            plantilla \texttt{.env.example} incluida en el repositorio. En él deben
            definirse la contraseña de la base de datos y, sobre todo, la clave de
            firma de los tokens (\texttt{JWT\_SECRET}), que ha de ser una cadena
            aleatoria de al menos 32 caracteres.
    
            \item Construir y arrancar los contenedores con la orden:
            \begin{verbatim}
            docker compose up -d --build
            \end{verbatim}
            La primera ejecución descarga las imágenes base y compila el proyecto,
            por lo que puede tardar unos minutos.
    
            \item Acceder a la aplicación desde un navegador en la dirección
            \texttt{http://localhost}.
        \end{enumerate}
    
        Al arrancar sobre una base de datos vacía, el catálogo de ejercicios se
        carga automáticamente y no existe ningún usuario, por lo que el primer paso
        dentro de la aplicación es registrar una cuenta. El estado de los servicios
        puede consultarse con \texttt{docker compose ps} y detenerse con
        \texttt{docker compose down}; añadir la opción \texttt{-v} a esta última
        orden elimina además los datos almacenados, dejando la base de datos limpia.
    
        \section*{Despliegue accesible desde Internet}
    
        Para exponer la aplicación en un servidor accesible desde Internet basta con
        ejecutar el mismo \texttt{docker compose} en una máquina con Docker y con los
        puertos 80 y 443 abiertos. Si en el fichero \texttt{.env} se asigna a la
        variable \texttt{SITE\_ADDRESS} un nombre de dominio en lugar del valor local
        por defecto, el proxy inverso obtiene y renueva automáticamente el
        certificado necesario para servir la aplicación sobre HTTPS, sin
        configuración adicional.
    
        \section*{Modo desarrollo}
    
        Para trabajar sobre el código con recarga en caliente se ejecuta únicamente
        la base de datos en contenedor, mediante \texttt{docker compose up -d mysql},
        y se arrancan por separado el backend, con Java~21 y Maven, y el frontend,
        con Node y el servidor de desarrollo de Angular. En esta configuración el
        cliente queda accesible en el puerto 4200 y el servidor en el 8080.
